# Bonny

Bonny is a small, private HTTP service that lets a trusted client work with a
[Turso](https://github.com/tursodatabase/turso) database through **structured JSON operations**. It never
accepts SQL from the caller: every statement is generated by the server from validated names and a restricted
operation model, and every value travels as a bound parameter. (It targets the Turso database engine,
version 0.8.2, not libsql.)

It runs either **local-only** (a Turso database file, in MVCC mode with concurrent write transactions) or as
an **embedded replica** that keeps a local copy synchronized with a remote Turso database.

**What it offers**

- **Schema:** create tables (several at once, atomically) with automatic or explicit primary keys and foreign
  keys; create and drop indexes; add, retype and rename columns; inspect the whole schema.
- **Writes:** atomic batch inserts and upserts into one table, or into several tables in one transaction;
  delete rows by filter, with safety guards.
- **Reads:** structured queries with filters (comparisons, `IN`, `LIKE`, `NULL`, ...), sorting, paging and joins.
- **Operations:** API-key authentication, request limits, consistent JSON errors, liveness and readiness
  probes, background sync in replica mode, structured logs and graceful shutdown.

**The use case behind it.** Bonny was designed around financial metrics keyed by ticker, metric and period
(quarterly or annual): a common read is the history of one metric of one ticker, and a common write is
periodically replacing all the metrics of a ticker. A table for that looks like this:

```json
{
  "name": "financial_metrics",
  "columns": [
    { "name": "ticker", "type": "TEXT" },
    { "name": "metric", "type": "TEXT" },
    { "name": "period", "type": "TEXT" },
    { "name": "value", "type": "REAL", "nullable": true }
  ],
  "primary_key": ["ticker", "metric", "period"]
}
```

The composite primary key enforces uniqueness and already serves lookups by ticker and metric followed by
period, so no extra index is needed for them. (Creating an index that merely repeats the key is allowed, but
the server logs a warning: add indexes for access paths you have measured, not by default.)

## Design decisions

- **No raw SQL, ever.** The caller sends operations, never statements. Table, column and index names are
  restricted to a safe character set and always quoted; column types come from an allowlist; filter operators
  come from an allowlist; every value is a bound parameter.
- **Validate first, write second.** Request shape, limits, names, values and, where possible, the live schema are
  checked before any transaction opens. Unknown request fields are rejected, so a typo is an error and never a
  silently ignored filter.
- **Atomic by default.** A batch (including a batch across several tables), a multi-table creation and a column
  type change are all-or-nothing. Atomicity is _local_: in replica mode a commit is not remote-durable until it is
  pushed.
- **Explicit for anything destructive.** A delete needs filters or an explicit `"all": true`, can carry a
  `max_rows` guard, and is checked exactly; a lossy type conversion needs an explicit opt-in;
  `INSERT OR REPLACE` is not offered because it deletes and reinserts rows (upserts update in place instead).
- **Idempotent schema operations.** Creating what already exists with the same definition is a success; a
  different definition is a conflict, never a silent no-op. Changing a column describes the end state, so
  repeating a request is harmless.
- **Concurrent writers, retried conflicts.** Local databases run in MVCC mode; when two writers touch the same
  row the loser is re-run for you, and only if it keeps losing does the client see a retryable `409`.
- **Honest, consistent errors.** One JSON error shape, meaningful status codes and machine-readable codes;
  internals are logged, not returned.
- **Safe defaults.** Listens on loopback only; authentication is required before listening elsewhere; every
  request has size, count and time limits; secrets are never logged; TLS is left to a reverse proxy.
- **Small surface.** One service, no ORM. Features are added one at a time (see the
  [roadmap](#limitations-and-roadmap)).

## Getting started

### Building from source

Bonny is built with a recent stable Rust toolchain (the project uses the 2024 edition; install it with
[rustup](https://rustup.rs)) plus a C compiler and `libclang`, because some dependencies compile native code:

```bash
sudo apt install build-essential clang libclang-dev pkg-config   # Debian/Ubuntu
sudo dnf install gcc clang clang-devel pkgconf                   # Fedora
cargo build --release                                            # produces target/release/bonny
```

The first build takes several minutes. If the build stops with an error about a missing `cc`, `clang` or
`libclang`, install the packages above. Use the `--release` binary for anything but development: debug builds
are much slower. The result is one self-contained program that can be copied anywhere.

### Local development: no configuration

```bash
cargo run
```

That is all. With no environment variables Bonny:

- listens on `127.0.0.1:3000` (this machine only),
- stores data in `./bonny.db` (created on first start; delete it to reset),
- has **authentication disabled** (it logs a warning at startup),
- runs **local-only**: no remote sync, no background worker, and the `/v1/sync/*` routes are not registered
  (they return 404).

Every feature without configuration is off. Each is switched on by setting its variable (see
[Configuration](#configuration)). To try the API from a terminal, follow the [curl walkthrough](#curl-walkthrough).

### Production

```bash
export API_KEY="$(openssl rand -hex 32)"      # turns authentication on
export LISTEN_ADDR=0.0.0.0:3000               # only allowed together with API_KEY
./target/release/bonny
```

See [Operations and security](#operations-and-security) for the checklist.

## Configuration

Everything is configured through environment variables, all optional:

| Variable                  | Default           | Meaning                                                                                                                                                                                        |
| ------------------------- | ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `API_KEY`                 | unset (auth off)  | Shared secret that turns authentication on. At least 32 characters and not one repeated character; set-but-empty is an error.                                                                  |
| `LISTEN_ADDR`             | `127.0.0.1:3000`  | Bind address. Without `API_KEY`, only loopback addresses are accepted: Bonny refuses to start on `0.0.0.0` and the like unauthenticated. Put TLS in front before exposing it beyond localhost. |
| `TURSO_LOCAL_PATH`        | `bonny.db`        | Local database file (its directory is created).                                                                                                                                                |
| `TURSO_DATABASE_URL`      | unset (no sync)   | Setting this selects **replica mode** and registers the sync routes (`libsql://`, `https://`, ...).                                                                                            |
| `TURSO_AUTH_TOKEN`        | required with URL | Token for the remote database.                                                                                                                                                                 |
| `IO_BACKEND`              | `default`         | Local mode only: `default`, `syscall` or `io_uring` (Linux). See [Linux: io_uring](#linux-io_uring-for-file-io).                                                                               |
| `SYNC_INTERVAL_SECS`      | `30`              | Replica mode: period of the background push-then-pull. `0` disables it.                                                                                                                        |
| `REQUEST_TIMEOUT_SECS`    | `30`              | Per-request timeout; see [Timeouts](#timeouts).                                                                                                                                                |
| `MAX_CONCURRENT_REQUESTS` | `64`              | In-flight requests before `429`.                                                                                                                                                               |
| `MAX_BODY_BYTES`          | `8388608` (8 MiB) | Largest request body; bigger ones get `413`. A body is held in memory, about 14 times its size while it is processed.                                                                          |
| `MAX_BATCH_STEPS`         | `20`              | Entries in a `batches` array per `/v1/batch` request.                                                                                                                                          |
| `MAX_BATCH_ROWS`          | `5000`            | Rows per `/v1/batch` request, **summed over all steps**.                                                                                                                                       |
| `MAX_BATCH_VALUES`        | `100000`          | Values (rows x columns) per `/v1/batch` request, summed over all steps.                                                                                                                        |
| `MAX_DELETE_ROWS`         | unset (no limit)  | If set, the most rows one `/v1/delete` request may remove; a delete that would remove more is rolled back (`409`). A request's own `max_rows` can only lower it.                               |
| `RUST_LOG`                | `info`            | Log filter (for example `bonny=debug` also logs conflict retries).                                                                                                                             |

Invalid values (zero, negative, not a number, a key that is too weak) stop the server at startup with a message
naming the variable.

**Authentication.** When `API_KEY` is set, send it as `x-api-key: <key>` or `Authorization: Bearer <key>`; it is
compared in constant time and never logged. The check runs before the request body is read. Without `API_KEY` no
credentials are checked and any key sent is ignored. `/health` and `/ready` never need a key.

**Replica mode** needs `TURSO_DATABASE_URL` and `TURSO_AUTH_TOKEN`; the local copy lives at `TURSO_LOCAL_PATH` and
is bootstrapped from the remote on first start. See [Replica mode and sync](#replica-mode-and-sync).

### Timeouts

Every `/v1` request has a timeout (`REQUEST_TIMEOUT_SECS`) and the database waits at most 5 seconds for a lock held
outside the process. Database work runs to completion even if the client disconnects or the timeout fires, so that
a transaction is never abandoned half-way. Consequence: **a `504` means "outcome unknown", not "it did not happen"**;
check before repeating a non-idempotent write.

## API conventions

### Requests and responses

- Every `/v1` request that has a body is JSON with `content-type: application/json` (`415` otherwise). Bodies are
  limited by `MAX_BODY_BYTES` (`413`, also a JSON error). Unknown fields are rejected (`400`).
- Success is `200` with a JSON body, or `204 No Content` with **no body** for creating tables and indexes, changing
  a table and dropping an index. `GET /v1/schema` and the probes are `GET`s.
- Wrong HTTP methods get `405`. Unknown routes get a JSON `404`.

### Errors

Every error is `{"error": "<what went wrong>", "code": "<machine-readable code>"}`:

| Status | `code`                             | Meaning                                                                                                                                                                |
| ------ | ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 400    | `bad_request`                      | Invalid input; the message says what and where (for example `batches[1]: ...`).                                                                                        |
| 401    | `unauthorized`                     | Missing or wrong API key.                                                                                                                                              |
| 404    | `not_found`                        | Unknown table, index or route (also the sync routes in local mode).                                                                                                    |
| 409    | `conflict`                         | A constraint (duplicate key, `NOT NULL`, foreign key), a name already taken, a table that exists with a different definition, or a schema change the database refuses. |
| 409    | `write_conflict`                   | Lost a write-write conflict even after the automatic retries. Nothing was written; send it again.                                                                      |
| 409    | `too_many_rows`                    | A delete would remove more rows than allowed. Nothing was deleted.                                                                                                     |
| 409    | `lossy_conversion`                 | A column type change would alter values. Nothing was changed.                                                                                                          |
| 413    | `payload_too_large`                | Body larger than `MAX_BODY_BYTES`.                                                                                                                                     |
| 415    | `unsupported_media_type`           | The body is not `application/json`.                                                                                                                                    |
| 429    | `too_many_requests`                | More than `MAX_CONCURRENT_REQUESTS` in flight; the answer carries `Retry-After: 1`.                                                                                    |
| 500    | `database_error`, `internal_error` | Unexpected; details are in the server log.                                                                                                                             |
| 503    | `unavailable`                      | The database is busy or unavailable; retry shortly.                                                                                                                    |
| 504    | `timeout`                          | The request took longer than `REQUEST_TIMEOUT_SECS`; for writes the outcome is unknown.                                                                                |

SQL and engine internals are logged, not returned. The exception is the message of a refused schema change you
asked for (it names the column or index from your own request), which is returned inside a `409`.

### Limits

| What                                              | Limit                                                                          |
| ------------------------------------------------- | ------------------------------------------------------------------------------ |
| Name of a table, column or index                  | up to 64 characters                                                            |
| Columns in a table / columns in an index          | 100 / 32                                                                       |
| Tables in one `POST /v1/tables` request           | 50                                                                             |
| Batch steps, rows, values per request             | `MAX_BATCH_STEPS` (20), `MAX_BATCH_ROWS` (5,000), `MAX_BATCH_VALUES` (100,000) |
| Request body                                      | `MAX_BODY_BYTES` (8 MiB)                                                       |
| Rows returned by a query                          | `limit` 1 to 500 (default 100); `offset` up to 1,000,000                       |
| Values in the filters of one query or delete      | 1,000                                                                          |
| Joined tables in one query                        | 5                                                                              |
| Rows removed by one delete                        | `MAX_DELETE_ROWS` (none by default) and the request's `max_rows`               |
| Requests in flight                                | `MAX_CONCURRENT_REQUESTS` (64)                                                 |
| Automatic retries of a write that lost a conflict | 10 attempts, short randomized backoff                                          |

### JSON values and SQLite values

| JSON                                   | SQLite                          |
| -------------------------------------- | ------------------------------- |
| `null`                                 | `NULL`                          |
| `true` / `false`                       | integer `1` / `0`               |
| integer literal in i64 range           | `INTEGER`                       |
| integer literal outside i64 range      | rejected (400), never rounded   |
| other number (`1.5`, `90753.0`, `1e3`) | `REAL`; non-finite rejected     |
| string                                 | `TEXT`                          |
| `{"$type":"blob","base64":"..."}`      | `BLOB` (also used for output)   |
| any other array/object                 | rejected; send JSON as a string |

On output, a `REAL` that is not finite becomes `null`. SQLite columns have type _affinity_, not
strict types: a `1` sent to a `REAL` column is stored and returned as `1.0`.

### Identifiers

Table, column and index names must match `[A-Za-z_][A-Za-z0-9_]{0,63}`, are always emitted double-quoted, are
compared case-insensitively for duplicates, and may not start with `sqlite_`, `turso_` or `__turso` (those belong
to the database engine). Names are therefore never a way to smuggle SQL into a request.

## API reference

| Method | Path              | Purpose                                                                   |
| ------ | ----------------- | ------------------------------------------------------------------------- |
| GET    | `/health`         | Liveness (no database access).                                            |
| GET    | `/ready`          | Readiness: opens a connection, runs `SELECT 1`, reports the journal mode. |
| POST   | `/v1/tables`      | Create one table, or several in one atomic request.                       |
| POST   | `/v1/indexes`     | Create an index.                                                          |
| POST   | `/v1/batch`       | Atomic batch insert / upsert, into one table or several.                  |
| POST   | `/v1/query`       | Structured query with filters, sort, paging and joins.                    |
| POST   | `/v1/delete`      | Delete the rows matching filters (or every row with `all: true`).         |
| GET    | `/v1/schema`      | List every table with its columns, primary key, foreign keys and indexes. |
| PATCH  | `/v1/table`       | Add a column, change its type and/or rename it.                           |
| DELETE | `/v1/index?name=` | Drop an index.                                                            |
| POST   | `/v1/sync/push`   | Replica mode only: push local changes.                                    |
| POST   | `/v1/sync/pull`   | Replica mode only: pull remote changes.                                   |
| GET    | `/v1/sync/status` | Replica mode only: sync health.                                           |

Each section below describes the rules of one endpoint. The [curl walkthrough](#curl-walkthrough) at the end runs
every one of them step by step.

Note that `PATCH /v1/table` and `DELETE /v1/index` are singular, while the create routes `POST /v1/tables` and
`POST /v1/indexes` are plural.

### `GET /health` and `GET /ready`

- `GET /health` answers `{"ok": true}` as long as the process is up. It never touches the database.
- `GET /ready` opens a database connection, runs a trivial query and answers
  `{"ok": true, "mode": "local" | "replica", "journal_mode": "mvcc", "sync_consecutive_failures": 0}`; if the
  database is unavailable it answers `503` (`unavailable`). A failing background sync does not make the service
  unready (the local database still serves); it shows up as `sync_consecutive_failures` and in
  `GET /v1/sync/status`.

### `POST /v1/tables`

```json
{
  "name": "notes",
  "columns": [
    { "name": "text", "type": "TEXT" },
    { "name": "done", "type": "INTEGER", "nullable": true }
  ]
}
```

Types: `INTEGER REAL TEXT BLOB NUMERIC` (case-insensitive). Columns are `NOT NULL` unless
`"nullable": true`. A table has 1 to 100 columns. Success is `204 No Content` with an empty body, both when the table was created
and when an identical one already existed.

**The primary key** is chosen with the optional `primary_key` field:

| `primary_key`          | Result                                                                                                                                                               |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| omitted (or `true`)    | **the default:** an `id INTEGER PRIMARY KEY` column is added as the first column, and the database assigns the id of every row you insert without one (1, 2, 3, ...) |
| `false`                | **no primary key at all**: no `id` column, and nothing prevents duplicate rows                                                                                       |
| `["ticker", "metric"]` | an explicit key over your own columns (composite if several); no `id` is added. Key columns cannot be nullable                                                       |

```json
{"name": "events", "columns": [{"name": "name", "type": "TEXT"}], "primary_key": false}
{"name": "financial_metrics", "columns": [ ... ], "primary_key": ["ticker", "metric", "period"]}
```

- With the default, **do not declare your own column named `id`**: it is reserved for the automatic
  key and the request is rejected (`400`) with a hint. Use an explicit key (`["id"]`) or `false` if
  you want to define `id` yourself. An explicit single `INTEGER` key column behaves the same way:
  leave it out of an insert and it is assigned too.
- In a batch, **leave `id` out of `columns`** to have it assigned, or include it to choose the
  value. Ids continue after the highest existing id, also after an explicit large one.
- The batch response does not return the generated ids; query the rows (filter on your own columns,
  or sort by `id desc`) to read them. Upserts need the key in the batch: with the automatic id,
  supply `id` and use `on_conflict` (the default `conflict_target` is the primary key); without a
  primary key, give a `conflict_target` that names a unique index, or use `"nothing"`.
- `primary_key: []`, a string, a number or an array with non-strings is rejected (`400`). A table
  without a key is spelled `false`; omitting the field gives the automatic `id`.
- **Why not `AUTOINCREMENT`?** The id is a plain `INTEGER PRIMARY KEY`, which SQLite already
  auto-assigns. The `AUTOINCREMENT` keyword makes every insert update one shared counter row, so
  concurrent writers conflict with each other under MVCC: in a test, 8 writers inserting 1,600
  rows without ids hit 535 write conflicts with `AUTOINCREMENT` and none without it. Its only extra
  guarantee is never reusing the id of a deleted row. Since rows can be deleted, this is what was
  observed in testing: in **local (MVCC) mode ids were never reused**, also after deleting the
  highest id, after deleting every row, and after a restart (observed behavior, not a documented
  guarantee of the engine). In **replica mode** (plain WAL) SQLite's usual rule applies:
  a new id is the current highest id plus one, so ids of deleted rows **can be reused** and the
  numbering restarts at 1 after every row was deleted. If you need strict never-reuse there, the
  fix is `AUTOINCREMENT` for non-MVCC databases (writes are serialized in replica mode anyway, so
  its concurrency cost would not apply); this has not been done.

**Foreign keys.** A column can reference a column of another table with `references`:

```json
{
  "name": "fact_values",
  "primary_key": false,
  "columns": [
    { "name": "symbol_id", "type": "integer", "references": "stocks" },
    { "name": "value", "type": "REAL", "nullable": true }
  ]
}
```

| `references`                            | Meaning                                                                  |
| --------------------------------------- | ------------------------------------------------------------------------ |
| `"stocks"`                              | `symbol_id` points at column `id` of table `stocks` (the default column) |
| `{"table": "stocks"}`                   | the same                                                                 |
| `{"table": "stocks", "column": "code"}` | `symbol_id` points at column `code` of `stocks`                          |

- **Enforcement:** inserting a row whose value has no matching row in the referenced table is
  rejected (`409`, "foreign key violation", the whole batch rolled back), and so is deleting a row
  that other rows still reference (`409`, "still referenced ...", nothing deleted). `NULL` is allowed in a
  nullable foreign key column and means "no reference". Bonny switches foreign key checking on for
  **every** connection (the engine leaves it off by default and per connection, so without this
  nothing would be enforced).
- **Checked when the table is created** (`400`, and nothing is created): the referenced table must
  **already exist** (create parents first), the referenced column must exist in it and be
  **unique on its own** (its single-column primary key, or a column with a unique index), and both
  columns must have the **same type**. A table may reference itself (for example `parent_id` of a
  tree table pointing at its own `id`); then the referenced column must be its own single-column key.
- **Order matters in `batches`:** a foreign key is checked immediately, so insert parents before
  children in one request. Delete children before parents (there is no cascading).
- **Idempotent like everything else:** repeating the same request is a `204`; the same table with
  different (or no) foreign keys is a `409`.
- **Limits of this feature:** the only constraint is the default one (`NO ACTION`): no `ON DELETE`
  or `ON UPDATE` actions such as `CASCADE`, and no composite (multi-column) foreign keys. Unknown
  fields inside `references` are rejected.
- **Index the foreign key column** (`POST /v1/indexes`) if the child table is large: without one,
  every delete from the parent has to scan the child table to see whether any row still refers to
  it. Bonny does not create that index for you.
- **A concurrency caveat (MVCC mode):** checks look at the snapshot a transaction started with.
  If one request inserts a child row while another, at the same moment, deletes its parent, both
  can succeed and leave an orphan (verified with two concurrent transactions against the engine).
  Sequential requests are always checked correctly. If that race matters, do not delete
  parents while children may be inserted, or run those operations one at a time. Replica mode
  serializes writes and is not affected.

**Several tables in one request.** `POST /v1/tables` also takes a list, which creates all the tables
**atomically**:

```json
{
  "tables": [
    { "name": "stocks", "columns": [{ "name": "symbol", "type": "text" }] },
    { "name": "metrics", "columns": [{ "name": "name", "type": "text" }] },
    {
      "name": "facts",
      "primary_key": false,
      "columns": [
        { "name": "stock_id", "type": "integer", "references": "stocks" },
        { "name": "metric_id", "type": "integer", "references": "metrics" },
        { "name": "value", "type": "real" }
      ]
    }
  ]
}
```

- Each element is exactly the body of a single-table request (`name`, `columns`, `primary_key`).
  The body is either one table or `{"tables": [...]}`; mixing them, or any other key next to `tables`,
  is a `400`. Success is `204`, and `{"tables": []}` is a no-op.
- **All or nothing:** everything is checked first, then the tables are created in one transaction. If any
  table fails (an invalid definition, a reference that cannot be satisfied, a name that is taken, an
  existing table with a different definition) **none of the new tables is created**. The error names the
  table: `tables[2] (table "facts"): ...`.
- **The order does not matter.** A foreign key may point at a table that appears later in the list (the
  example above works with `facts` first), and tables may even reference each other. A reference to a
  table of the same request is checked against that table's definition: the referenced column must be
  its single-column primary key (the default `id`, or the key you declared) and have the same type.
  References to tables that already exist are checked against the database, as before.
- **Idempotent:** sending the same request again is a `204`. Tables that already exist with an identical
  definition are left alone (with their data) and the missing ones are created; one that exists with a
  _different_ definition is a `409` for the whole request.
- A table name may appear only once in a request, and at most 50 tables can be created in one request.
- Schema changes wait for a quiet moment: while writers are busy the creation is retried a few times,
  and writers caught in the middle are retried too (the same as for `PATCH /v1/table`).

`CREATE TABLE IF NOT EXISTS` is not used because it would accept an existing table of a different
shape. Instead an existing table is compared against the request (columns, primary key and foreign
keys): identical -> `204` (nothing to do); different -> `409`. Indexes work the same way (name, table,
uniqueness and column order must all match).

### `POST /v1/indexes`

```json
{ "name": "idx_period", "table": "financial_metrics", "columns": ["period"], "unique": false }
```

The table and columns must exist (`404` / `400`), an index has 1 to 32 columns, and the name must not
be used by a table or by an index with another definition (`409`). Success is `204 No Content` with an empty body (also when an
identical index already existed). An index that merely duplicates the primary key's own index is
still created, but the server logs a warning; check a query plan before keeping it. Creating a unique
index over data that already contains duplicates is refused (`409`) and creates nothing.

### `POST /v1/batch`

Inserts or upserts rows into one table, or into several tables **in one transaction**.

```json
{
  "table": "financial_metrics",
  "columns": ["ticker", "metric", "period", "value"],
  "rows": [["AAPL", "revenue", "2024-Q1", 90753.0]],
  "on_conflict": { "replace": ["value"] },
  "conflict_target": ["ticker", "metric", "period"]
}
```

To write several tables atomically, wrap the same objects in a `batches` envelope. The steps run
in array order inside one transaction:

```json
{
  "batches": [
    { "table": "companies", "columns": ["ticker", "name"], "rows": [["AAPL", "Apple"]] },
    {
      "table": "financial_metrics",
      "columns": ["ticker", "metric", "period", "value"],
      "rows": [["AAPL", "revenue", "2024-Q1", 90753.0]],
      "on_conflict": "replace_all"
    }
  ]
}
```

- Each step is a complete batch object with its own `columns`, `on_conflict` and
  `conflict_target`. The same table may appear in more than one step.
- **All-or-nothing:** if any step fails, every step is rolled back, including earlier tables.
  Errors name the step, for example `batches[1] (table "financial_metrics"): constraint violation
at row 2; the whole request was rolled back`.
- **Validated up front:** the body shape, limits, identifiers, values and conflict options of every
  step, then every table and column against the live schema, are checked before the transaction
  opens. A mistake in step 5 writes nothing from steps 1-4.
- **No data flows between steps.** A step cannot use a value generated by an earlier one; supply
  all values (including keys) in the request.
- The envelope must be an object with only the `batches` key; it cannot be combined with a
  top-level `table`/`rows`. A bare top-level array is rejected. `{"batches": []}` is a valid no-op.
- A step with an empty `rows` array is skipped (not even checked against the schema); if every step
  is empty no transaction is opened.

**Limits** apply to the whole request, summed over its steps (configurable, see the environment
table): `MAX_BATCH_STEPS` (20), `MAX_BATCH_ROWS` (5,000), `MAX_BATCH_VALUES` (100,000) and
`MAX_BODY_BYTES` (8 MiB). Raising the row or value limits may require raising `MAX_BODY_BYTES`.
The two row/value limits work together: a request may hold up to 5,000 rows **and** up to 100,000
values, so 5,000 rows of up to 20 columns fit (a 20-column table at 5,000 rows is exactly
100,000 values), while 5,000 rows of 21 columns do not. Raise `MAX_BATCH_VALUES` for wider tables.
The body must also fit in `MAX_BODY_BYTES`: a realistic 5,000 x 20 request (numbers and short
strings) is about 1 MiB, with 40-character text values about 2.7 MiB and with 120-character values about
6.5 MiB, so the 8 MiB default covers it. Measured on the release build, such a batch commits in well under
0.1 s, and the server needs roughly 14x the body size in memory while it processes it (about 90 MiB for the
6.5 MiB case), so keep `MAX_BODY_BYTES` x `MAX_CONCURRENT_REQUESTS` in mind when raising it.

In local mode the transaction is a `BEGIN CONCURRENT` one (see [Concurrency](#concurrency-mvcc-durability-and-sync)): on a write-write
conflict the **whole request** is re-run, so tables never get out of step. In replica mode it is a
`BEGIN IMMEDIATE` transaction behind the in-process write lock.

`on_conflict`:

| Value                    | SQL                                                             |
| ------------------------ | --------------------------------------------------------------- |
| `"abort"` (default)      | plain `INSERT`; a constraint violation fails the request        |
| `"nothing"` / `"ignore"` | `INSERT OR IGNORE`                                              |
| `"replace_all"`          | `ON CONFLICT (target) DO UPDATE` for every non-key batch column |
| `{"replace": [cols]}`    | `ON CONFLICT (target) DO UPDATE` for just those columns         |

`conflict_target` defaults to the table's primary key and must equal the columns of the primary
key or of a non-partial unique index. `INSERT OR REPLACE` is deliberately not offered: in SQLite
it _deletes_ the conflicting row and inserts a new one, so any column not in the batch silently
reverts to its default. The upsert modes update the existing row in place.

**Response** (the same shape for a single batch and for `batches`):

```json
{
  "rows": { "submitted": 3, "affected": 2 },
  "batches": { "companies": { "submitted": 1, "affected": 1 }, "financial_metrics": { "submitted": 2, "affected": 1 } }
}
```

- `submitted` is the number of rows you sent; `affected` is the number the database reports as
  inserted or updated. They are equal unless rows were skipped: with `"nothing"`, rows that
  already exist are not counted in `affected`, so `submitted - affected` is the number skipped.
  (For upserts, inserts and updates both count as 1, so they cannot be told apart.)
- `rows` is the total over all steps. `batches` is keyed by table, in order of first appearance;
  if several steps write the same table their counts are added up.

### `POST /v1/query`

```json
{
  "table": "financial_metrics",
  "columns": ["period", "value"],
  "filters": { "ticker": "AAPL", "metric": { "in": ["revenue", "profit"] }, "value": { "gt": 1, "lt": 100000 } },
  "sort": [{ "period": "asc" }, { "ticker": "desc" }],
  "limit": 100,
  "offset": 0
}
```

**`filters`** maps a column to a condition; conditions on different columns are combined with AND.

| Condition                                  | SQL                                  |
| ------------------------------------------ | ------------------------------------ |
| `"col": 5` / `"x"` / `true`                | `col = ?`                            |
| `"col": null`                              | `col IS NULL`                        |
| `"col": {"eq": v}` / `{"ne": v}`           | `col = ?` / `col <> ?`               |
| `{"gt": v}` `{"gte": v}`                   | `col > ?` / `col >= ?`               |
| `{"lt": v}` `{"lte": v}`                   | `col < ?` / `col <= ?`               |
| `{"in": [a, b]}` / `{"not_in": [...]}`     | `col IN (?, ?)` / `col NOT IN (...)` |
| `{"like": "f%"}` / `{"not_like": "f%"}`    | `col LIKE ?` / `col NOT LIKE ?`      |
| `{"is_null": true}` / `{"is_null": false}` | `col IS NULL` / `col IS NOT NULL`    |

- An object may hold several operators; they are ANDed (`{"gt": 1, "lt": 9}` is a range).
- `like` takes one pattern or an array of patterns. With an array, `like` matches **any** pattern
  (OR) and `not_like` matches **none** (AND), mirroring `in` / `not_in`. `%` matches any run of
  characters and `_` exactly one; matching is case-insensitive for ASCII letters (SQLite's default).
- Operands are scalars (string, number, boolean) or tagged blobs. `null` is not allowed inside an
  operator (use `is_null`). `in` / `not_in` take an array of such scalars; an empty `in` matches
  nothing and an empty `not_in` matches everything. At most 1,000 values per query across all filters.
- SQL's NULL rules apply: a comparison (`ne`, `gt`, `not_in`, `not_like`, ...) is never true for a
  NULL cell, so those rows are excluded. Ask for them with `is_null`.
- Mistakes are 400s naming the column and the problem: an unknown operator, an empty operator
  object, a wrong operand type, an unknown column.
- A filter value that is an object with a `$type` key is a tagged blob (`eq`), not an operator map.

**`sort`** is an array with one single-column object per sort key, each `"asc"` or `"desc"`
(case-insensitive). The array order is the priority: `[{"period": "asc"}, {"id": "desc"}]` sorts by
period, then by id descending. Every entry must have exactly one column, and a column may appear
only once. The earlier object form (`{"period": "asc"}`) and the old `order_by` field are rejected
with a `400`.

**Other fields**

- `columns` omitted/empty means all columns, in declared order.
- `limit` defaults to 100 and must be between 1 and 500 (over-limit is an error, not a silent clamp).
  `offset` is at most 1,000,000 and requires a `sort` so pages are deterministic.
- The table and every column mentioned in `columns`, `filters` and `sort` are checked against the
  live schema first (404 / 400).

**Joins.** Add `join` to bring in columns of other tables. Each joined table is mapped to the column of
the base table (`table`) that holds its key:

```json
{
  "table": "fact_values",
  "join": { "stocks": "symbol_id", "facts": "fact_id" },
  "columns": { "fact_values": ["value", "ordinal"], "stocks": ["symbol"], "facts": ["name"] },
  "filters": { "facts.name": "eps", "stocks.symbol": "AAPL", "frequency": 1 },
  "sort": [{ "ordinal": "asc" }]
}
```

```json
{ "rows": [{ "value": 1.2, "ordinal": 2, "symbol": "AAPL", "name": "eps" }], "row_count": 1 }
```

- **What is compared.** `"stocks": "symbol_id"` means `fact_values.symbol_id = stocks.<key>`. The
  `<key>` is the column the foreign key of `symbol_id` points at (declared with `references` when the
  table was created); with no such foreign key it is the joined table's `id`; and if there is no `id`
  either, the request is a `400` that shows how to spell it out. Spell it out with the object form:
  `{"stocks": {"column": "symbol_id", "to": "code", "type": "left"}}`, where `column` belongs to the
  base table, `to` to the joined table, and `type` is `"inner"` (default) or `"left"`. This also allows
  joining a parent to its children (`{"fact_values": {"column": "id", "to": "symbol_id"}}`), which
  returns one row per child.
- **Inner or left.** An inner join leaves out rows without a match; a `left` join keeps every row of
  the base table, with `null` for the columns of the joined table when nothing matches.
- **`columns` is required with `join`** (no `*`, since the tables would clash on `id`). It can be an
  object per table (above), a list containing such an object (`[{"fact_values": [...], ...}]`), or a
  list of names with the table in front where needed (`["fact_values.value", "stocks.symbol"]`). Result
  rows have the columns in the order asked, under their plain names.
- **Two columns with the same name** (say both tables have `id`) would give a result with duplicate keys,
  so that is a `400` until you rename one: `{"stocks": [{"column": "id", "as": "stock_id"}]}`.
- **Naming columns elsewhere.** In `filters` and `sort`, write `table.column`. A name without a table is
  accepted when exactly one table of the query has that column; if several do (`name` in both `stocks`
  and `facts`) it is a `400` asking you to qualify it. A table that is not part of the query, or a
  column that does not exist, is a `400` (an unknown name is never read as text). Filters accept all the
  usual operators on joined columns, and `offset` still needs a `sort`.
- **Limits:** at most 5 joined tables, each joined directly to the base table (not through another
  joined table), the same table only once, and never the base table itself. Aliasing a table (to join
  it twice) is not supported. A missing table is a `404`.
- Without `join` nothing changes. `table.column` names and `as` are only for queries with `join`; a
  plain query may still write `columns` as an object or list-of-objects for the base table.
- Joins are fastest on indexed columns; a primary key always is. Index the columns you join on
  (`POST /v1/indexes`), especially a foreign key column of a large table.

Response: `{"rows": [{...}], "row_count": n}`.

### `POST /v1/delete`

Deletes the rows of one table that match filters.

```json
{ "table": "financial_metrics", "filters": { "ticker": "AAPL", "period": { "like": "2023-%" } }, "max_rows": 100 }
```

```json
{ "rows": { "deleted": 4 } }
```

- **`filters`** use exactly the grammar of `/v1/query` (plain values, `null`, and the operators
  `eq ne gt gte lt lte in not_in like not_like is_null`; conditions are ANDed), with the same
  validation: an unknown table is a `404`, an unknown column a `400`. That check also guards against a
  typo silently matching every row, because the database would otherwise read an unknown
  double-quoted name as a string literal. Blobs work as in queries.
- **A forgotten filter cannot wipe a table:** `filters` is required. A missing or empty `filters`
  is a `400`. To delete **every** row you must say so with `"all": true`, and `all` cannot be
  combined with filters.
- **`max_rows`** (optional) is a guard: if the delete would remove more than this many rows,
  **nothing is deleted** and the answer is `409` with code `too_many_rows` and the actual count.
  It is checked exactly, inside the transaction, so there is no count-then-delete race. It also
  applies to `all`. It must be at least 1.
- **`MAX_DELETE_ROWS`** (server setting, **unset = no limit** by default) is a ceiling for every
  delete; a request's `max_rows` can only lower it, never raise it.
- Deleting nothing is a success: `{"rows": {"deleted": 0}}` with `200` (so a retry is safe). A
  missing table is a `404`.
- Only `table`, `filters`, `all` and `max_rows` are accepted; there is no `sort`, `limit` or
  returning of the deleted rows.
- The delete is a single transaction. In local (MVCC) mode it is a `BEGIN CONCURRENT` one with the
  same conflict handling as batches: it removes the rows **visible when it started**, so a matching
  row that another request inserts at the same moment is not deleted (it simply is not part of
  this delete), and if another transaction changes a row it wants to delete, the engine reports a
  write-write conflict and the whole delete is re-run; after repeated losses the answer is `409`
  `write_conflict` with nothing deleted. Unlike inserts, a very large delete is not capped by
  default, so use `max_rows` (or `MAX_DELETE_ROWS`) if you want a safety net.

### `GET /v1/schema`

Describes the whole schema in the vocabulary of `POST /v1/tables` and `POST /v1/indexes`. No
parameters, no body.

```json
{
  "tables": [
    {
      "name": "stocks",
      "primary_key": ["id"],
      "columns": [
        { "name": "id", "type": "INTEGER", "nullable": false, "auto_id": true },
        { "name": "code", "type": "TEXT", "nullable": false, "auto_id": false },
        {
          "name": "owner_id",
          "type": "INTEGER",
          "nullable": true,
          "auto_id": false,
          "references": { "table": "people", "column": "id" }
        }
      ],
      "indexes": [{ "name": "u_stocks_code", "unique": true, "columns": ["code"] }]
    }
  ]
}
```

- **Order:** tables are sorted by name, columns are in declaration order, indexes are sorted by name.
- **`primary_key`** is the list of key columns in key order, or `[]` for a table without one.
- **`nullable`** is whether the column accepts `NULL`. Key columns never do.
- **`auto_id`** is `true` for the single `INTEGER` primary key column, which the database fills in
  when an insert leaves it out (the automatic `id`, or an explicit lone `INTEGER` key).
- **`references`** is present only on foreign key columns, in the form used to create them.
  The default column shows up as the column it resolves to (`"id"`).
- **`indexes`** lists the indexes made with `CREATE INDEX` (that is, by `POST /v1/indexes`), with
  `unique` and the indexed `columns` in index order; an index with a `WHERE` clause has
  `"partial": true`. The primary key's own index and the automatic indexes of `UNIQUE` constraints
  are not listed (the key is in `primary_key`).
- **Types** are returned in capitals (`INTEGER`, `REAL`, `TEXT`, `BLOB`, `NUMERIC`).
- **Left out:** the database's own bookkeeping tables (MVCC keeps one), views, tables whose names the
  API cannot address (reserved prefixes, characters outside the identifier rules), and composite
  foreign keys, which Bonny cannot create. An empty database answers `{"tables": []}`.
- **Consistent:** the whole answer is read in one transaction, so it is a single snapshot even if
  tables or indexes are created at the same moment. It is a read: it does not block or wait for
  writers, and it needs the API key like every other `/v1` route.
- The answer includes **every** table, so on a database with very many tables it can get large.

### `PATCH /v1/table`

Changes one column of an existing table: **adds** it if it is missing, **changes its type** if it
differs, **renames** it if asked. (Note the spelling: this route and `DELETE /v1/index` are
singular, while the create routes `POST /v1/tables` and `POST /v1/indexes` are plural.)

```json
{ "table": "readings", "column": "amount", "type": "integer", "rename": "weight" }
```

| Field             | Meaning                                                                                                            |
| ----------------- | ------------------------------------------------------------------------------------------------------------------ |
| `table`, `column` | the column to look at (required)                                                                                   |
| `type`            | the type the column must have: `INTEGER REAL TEXT BLOB NUMERIC`, case-insensitive                                  |
| `rename`          | the name the column must have                                                                                      |
| `nullable`        | only when **adding**: `true` for a column that accepts `NULL`; default `false` (NOT NULL), as in `POST /v1/tables` |
| `references`      | only when **adding**: a foreign key, `"stocks"` or `{"table": "stocks", "column": "code"}`                         |
| `default`         | only when **adding**: the value the existing rows get (it is used once; the column gets no default)                |
| `lossy`           | `true` to allow a type conversion that changes some values (see below)                                             |

At least one of `type` and `rename` is required. The answer is always `204 No Content`.

**The request describes how the column should end up, so repeating it is harmless:**

- The column exists and already looks like that: nothing happens (`204`).
- The column does not exist: it is **added** (`type` is required; `rename` is not allowed here).
- The column does not exist **but `rename` does**: an earlier request already renamed it, so the
  new name is used for the rest. Repeating `{"column": "amount", "rename": "weight"}` never creates a
  fresh, empty `amount`.
- The type differs: it is converted. `rename` differs: it is renamed (type first, then name).
- For an existing column `nullable` and `references` are accepted only if they agree with what is
  there (otherwise `409`: those cannot be changed); `default` is ignored.

**Adding a column.** A nullable column is added in place (with `default`, existing rows get that value
instead of `NULL`). A NOT NULL column cannot be added in place (the engine would force a permanent
`DEFAULT` on it), so the table is rebuilt: a table **with rows needs `default`**, or `"nullable": true`
(`400` otherwise); a default that does not fit the type is a `400`. `references` is checked like in
`POST /v1/tables` (the parent must exist, be unique and have the same type), except that a column
cannot reference its own table when it is added.

**Changing a type.** Only `INTEGER`, `REAL` and `TEXT` columns can be converted between each other.
The values are cast, which silently changes some of them, so Bonny first checks every value: a value is
fine when converting it there and back gives it back. These are refused with `409` and code
`lossy_conversion`, with the number of affected values and a few examples, **before anything is changed**:
text such as `"007"`, `" 5 "`, `"3.9"` (to an integer), `"abc"` or `""` (which would become `0`), a real
such as `3.5` (to an integer), or an integer too large for a real. Send `"lossy": true` to convert them
anyway (they are cast: `"abc"` becomes `0`, `3.9` becomes `3`). Anything converted to `TEXT` is always
exact; `NULL` stays `NULL`.

How the table is changed depends on the column, and it all happens **in one transaction** (any failure
undoes everything):

- **Nullable column: changed in place.** A new column of the new type is added, the cast values are
  copied into it, the old column is dropped and the new one takes its name. Other tables that reference
  this table are not affected. **The column moves to the end of the table**, and indexes on it are
  recreated.
- **NOT NULL column: the table is rebuilt.** A copy with the new definition is created, the rows are
  copied, the old table is dropped and the copy renamed, and the indexes are recreated. Column order,
  `NOT NULL`, the primary key, foreign keys and row ids are all kept. Since the engine cannot drop a
  table that others reference, a **NOT NULL column of a referenced table is refused** (`409`).
- Both are refused (`409`) for a primary key column, a foreign key column, and a column that another
  table's foreign key points at. A rebuild is also refused for tables Bonny could not reproduce exactly:
  those with a column default, a `UNIQUE` constraint, triggers, `CHECK`, `COLLATE`, foreign key actions
  or composite foreign keys (tables made by Bonny have none of these). In every refusal nothing is changed.
- If the converted data breaks a unique index (`"1"` and `"01"` both become `1`), the engine refuses
  and the whole change is undone (`409`).

**Renaming** uses the engine's own `RENAME COLUMN`: indexes and the foreign keys on both sides follow
the new name, and the table keeps its data. A name that is already taken is a `409`; a name that
differs only in letter case is a `400`. Clients that still use the old name get `400`s.

**Cost and concurrency.** Changing a type touches every row, so it takes time in proportion to the
table (measured on a development machine with 200,000 rows: under a second) and queues behind other
schema changes.
Writers that were in flight when the schema changed are retried automatically. While the database is
very busy the change itself is retried a few times too; if it still cannot get through, the answer is
`409` with code `write_conflict` and nothing was changed, so just send it again. Replica mode (WAL) is
not affected by MVCC conflicts, but **schema changes have not been verified against a remote
database**.

**Not supported:** dropping a column, changing nullability, adding or removing a foreign key on an
existing column, defaults, and converting from or to `BLOB` / `NUMERIC`.

### `DELETE /v1/index?name=<index>`

Drops an index, for example one made with `POST /v1/indexes` that is no longer needed. Success is
`204 No Content`.

```
DELETE /v1/index?name=idx_metrics_metric_period
```

- An unknown index is a `404` (not a silent success, since the name is the whole request); a name that
  belongs to a table is a `400`; a missing `name`, extra query parameters, or an invalid or reserved
  name (the automatic `sqlite_autoindex_...` indexes) are `400`s.
- **An index that a foreign key depends on is refused** (`409`, nothing dropped): the unique index that
  makes a column unique for another table's foreign key (like `u_stocks_code` when `watchlist.code`
  references `stocks.code`). The engine would drop it and then reject every later insert into the child
  table. An index on the primary key column itself, or on a column nobody references, can be dropped.
- A table's own primary key index is not an index you can drop; `GET /v1/schema` lists the ones you can.
- Dropping an index changes no data. Queries that used it just get slower, and an upsert that named it as
  its `conflict_target` is refused from then on.

### Sync endpoints (replica mode only)

These routes exist only when `TURSO_DATABASE_URL` is set; otherwise they are plain `404`s.

- `POST /v1/sync/push` sends local commits to the remote database: `{"ok": true}`.
- `POST /v1/sync/pull` fetches remote changes: `{"ok": true, "changed": true | false}`.
- `GET /v1/sync/status` reports the health of syncing: `ok`, `last_push_unix`, `last_pull_unix`, `last_error`,
  `last_error_unix`, `consecutive_failures`, `pending_local_changes` (changes not pushed yet), `revision`,
  `network_sent_bytes` and `network_received_bytes`.

A background worker also pushes and then pulls every `SYNC_INTERVAL_SECS`, so the endpoints are only needed to
force a sync. Push and pull never run at the same time, a failure is recorded in the status and retried at the next
tick, and a final push is attempted when Bonny shuts down gracefully. See
[Replica mode and sync](#replica-mode-and-sync) for the guarantees.

## Concurrency (MVCC), durability and sync

### Local mode: MVCC with concurrent writers (the default)

On startup Bonny puts the local database into MVCC mode (`PRAGMA journal_mode = 'mvcc'`) and
checks that it took effect; `GET /ready` reports `"journal_mode": "mvcc"`. There is nothing to
configure.

- **Readers never block and are never blocked.** Each query sees a consistent snapshot.
- **Batches run in parallel.** Each `POST /v1/batch` is its own `BEGIN CONCURRENT` transaction on
  its own connection. Batches that touch different rows (different tickers, say) commit
  independently without waiting for each other.
- **Conflicts are first-committer-wins.** If two in-flight batches change the same row, the first
  to commit wins and the other is aborted by the engine with a "write-write conflict". Bonny
  re-runs the aborted batch automatically on a fresh connection (up to 10 attempts with a short
  randomized backoff), so the client normally never notices. Retried batches see the winner's
  data, so with `replace_all` on the same rows the last committer's values are the final state;
  a batch is never half-applied or mixed with another's rows.
- **If it keeps losing**, the request answers `409` with `"code": "write_conflict"`. Nothing was
  written; it is safe to retry. (A _constraint_ violation such as a duplicate primary key is also
  a 409, but with `"code": "conflict"` and is not retried: it would fail the same way again.)
- **Schema changes are exclusive.** Creating tables or indexes and changing columns need an
  exclusive transaction, so schema requests queue behind each other in-process. A data batch that was in
  flight when the schema changed fails with a "schema conflict" and is retried the same way, and a schema
  change that finds the database busy is itself retried a few times (then `409 write_conflict`, nothing
  changed).
- The mode is stored in the database file. An existing database created earlier in WAL mode is
  converted on the first start (data is kept). Converting it back is untested. MVCC adds a
  `*.db-log` file next to the database and an internal table, `__turso_internal_mvcc_meta`, which
  Bonny reserves and does not expose through the API names it accepts (names starting with
  `sqlite_`, `turso_` or `__turso` are rejected).
- A development test with a release build (16 parallel writers, 160 batches of 200 rows): on disjoint
  rows there were no conflicts and it took 0.13 s; all writers rewriting the _same_ 200 rows caused 280
  conflicts, all retried transparently, every request succeeded (0.42 s), and the final table held a
  single writer's values. Treat the numbers as indicative only.

### Replica mode and sync

In replica mode (`TURSO_DATABASE_URL` set) the local file is a copy of a remote Turso database that is synchronized
in both directions. Bonny keeps local and remote durability apart on purpose:

- A batch (or any write) is atomic on the **local** database. It is not durable remotely until pushed; the background
  worker pushes and then pulls every `SYNC_INTERVAL_SECS`, and sync failures are visible in `GET /v1/sync/status`
  and as `sync_consecutive_failures` on `/ready`.
- Push and pull never run concurrently.
- A final push is attempted on graceful shutdown.
- Replica databases are **not** switched to MVCC: the sync engine manages that file's journal and MVCC with it has
  not been verified. They keep the default single-writer mode, so batches, deletes and schema changes queue behind
  an in-process lock instead of running in parallel.
- Foreign keys are enforced here too, and a concurrent parent-delete / child-insert race cannot happen because
  writes are serialized.

What has **not** been verified: replica mode has not been exercised against a real remote database. Unverified are
replication of the schema changes (tables, indexes, type changes, renames), push/pull/restart behavior, and
multi-writer conflict behavior. Treat replica mode as experimental until you have tested your own setup.

### All modes

- Each request uses its own database connection (with foreign key checking switched on). A 5 s busy timeout covers
  writers outside this process.
- Database work runs to completion even if the client goes away or the request times out (see
  [Timeouts](#timeouts)).
- Readers never wait for writers; a read-only query or schema listing sees one consistent snapshot.

## Operations and security

- **Network:** Bonny listens on `127.0.0.1` by default. It serves plain HTTP; to expose it beyond the machine put
  TLS in front (a reverse proxy) and set `API_KEY`. Without a key Bonny refuses to listen on a non-loopback address.
- **Secrets:** use a long random `API_KEY` (at least 32 characters; `openssl rand -hex 32`), keep it out of source
  control and out of command lines (a service environment file with mode 600 works well). It is never logged:
  request logs contain the method, path, status and duration, but no headers and no values.
- **Authentication scope:** a single shared key, with no per-client rate limiting or failed-attempt throttling. The
  global `MAX_CONCURRENT_REQUESTS` cap is the only load shedding (`429`).
- **Limits:** every request is bounded in size, row and value counts, result size and time (see [Limits](#limits)).
  Query results are capped at 500 rows; use `limit` and `offset` to page.
- **Errors:** clients get generic, structured errors; details go to the log (`RUST_LOG`).
- **Probes:** use `/health` for liveness and `/ready` for readiness.
- **Shutdown:** `SIGINT` and `SIGTERM` trigger a graceful shutdown: in-flight requests finish first, the background
  sync stops, and in replica mode a last push is attempted.
- **Backups:** the MVCC storage mode is young (see [Limitations](#limitations-and-roadmap)); keep backups of the
  database file.

### Running as a service

For example as a systemd unit, `/etc/systemd/system/bonny.service`:

```ini
[Service]
ExecStart=/opt/bonny/bonny
Environment=TURSO_LOCAL_PATH=/var/lib/bonny/bonny.db
EnvironmentFile=/etc/bonny.env      # put API_KEY=... in here, mode 600
Restart=on-failure
```

### Linux: `io_uring` for file IO

By default the database reads and writes its file with ordinary blocking system calls, which briefly occupy a
server thread. On Linux, `io_uring` lets the kernel do that work in the background, so the thread is free to serve
other requests. It is **off by default**, applies to **local mode** only (replica mode rejects it), and does
nothing on macOS or Windows. It will not make a commit's `fsync` faster; the possible gain is better behavior under
many concurrent writes or cache-missing reads, so measure under your own load before relying on it.

```bash
export IO_BACKEND=io_uring
./target/release/bonny            # the startup log shows:  ... mode="local" ... io=IoUring
```

Accepted values are `default`, `syscall` (plain blocking calls) and `io_uring`. Bonny never falls back silently: if
`io_uring` is unavailable it exits at startup with an error that mentions `io_uring`. Common causes:

- **Old kernel:** use a modern 5.x or 6.x kernel (the exact minimum is not verified).
- **Container sandbox:** recent Docker/containerd default security profiles block `io_uring`. Either run without
  `IO_BACKEND` or allow the syscalls in a custom seccomp profile (`--security-opt seccomp=<profile.json>`);
  unconfined seccomp works but is a security trade-off.
- **Hardened host:** some distributions disable it with the `kernel.io_uring_disabled` sysctl (`0` means allowed).

To double-check it is in use, start Bonny under `strace -f -e trace=io_uring_setup`. The `io_uring` path has been
developed on macOS, where it cannot run; it has not yet been exercised on a real Linux machine.

## SQL injection and input safety

**Bonny is not open to SQL injection through its API, as far as a full read of the code and an attack-style test suite can show.** No route accepts SQL. Every statement is assembled on the server from three kinds of
parts, and each kind has its own defense. A request can only influence a statement through these three; it can never add to the SQL text itself.

| Part of the statement | Where it comes from | Defense |
| --- | --- | --- |
| **Values** (filter operands, `in` lists, `like` patterns, batch rows, upsert values, `PATCH` defaults) | The request | Never put into the SQL text. Every one is a bound parameter (`?1`, `?2`, ...), so `' OR '1'='1` is compared or stored as a plain string. A literal `?1`, `:a` or `$a` inside a value is just text. |
| **Names** (tables, columns, indexes, join columns, the `to` side of a join, referenced columns) | The request | SQL cannot bind names, so each one must match `[A-Za-z_][A-Za-z0-9_]*`, be at most 64 characters, and not start with `sqlite_`, `turso_` or `__turso`. Anything else is a `400` before any SQL exists. An accepted name is then double-quoted. The rule is ASCII-only, so look-alike letters, invisible characters, `--`, `/*`, quotes, semicolons and `\0` never get through. |
| **Keywords** (column types, filter operators, `ASC` / `DESC`, `LEFT` join, `LIMIT`, `OFFSET`) | The request picks, the server writes | Chosen from fixed sets: a type must be one of the five allowed names, an operator maps to a fixed fragment (`=`, `<>`, `LIKE`, ...), the sort direction and join type are one of two words, and `limit` / `offset` are parsed as unsigned integers before they are printed. |

Other points that matter for the answer:

* **Names read back from the database** (for example while `PATCH /v1/table` rebuilds a table, or when it lists
  indexes) are quoted with every embedded `"` doubled, so even an unusual name written to the file by another tool
  cannot end the identifier early.
* **Names are also checked against the live schema.** Every column a request mentions must exist in the table, which
  also means a typo can never fall through to SQLite's habit of reading an unknown `"double-quoted"` name as a string
  literal.
* **Authentication comes first.** The API key is checked before the request body is read, so an unauthenticated
  caller cannot even get a hostile payload parsed (see [Operations and security](#operations-and-security)).
* **Error messages** that repeat a name show it JSON-escaped and cut to 64 characters. Failures of data operations
  are logged on the server and reach the client only as a generic message. A refused schema change (`PATCH`, create
  table or index) may quote the database's short reason, which names only things that came from the request; the
  statement text is never returned.
* **No raw SQL anywhere**, by design: there is no field, header or query parameter that is passed to the database as
  SQL, and no feature (such as a computed column or a custom sort expression) that would need one.

### What this does not cover

* **`like` patterns keep their wildcards.** `%` and `_` in a `like` pattern are meant to work, and a pattern with
  many wildcards can be slow on a large table. That is a cost, not an injection: the pattern can only match text in the
  column you named. Requests are bounded by the [limits](#limits) (at most 1,000 filter values, a request timeout and a
  concurrency cap).
* **The database file itself.** Anyone who can write to the file directly (or to the remote database) is outside what
  an HTTP API can protect. Bonny trusts the schema it finds there only in the ways described above.
* **A stolen API key** lets the holder do everything the API allows (including deleting data). Keep the key
  secret and put the service behind TLS or a trusted proxy when it is reachable from a network.
* **Leniency found while writing the tests:** `"columns": [{}]` (an empty per-table mapping inside a column list)
  is accepted and selects every column, because an empty mapping names no column. It cannot reach SQL.

### How it is tested

`cargo test sqli_` runs the whole suite in about a second. It attacks each layer:

* **The name rules**, with a fuzz of 30,000 strings built from SQL, JSON and URL metacharacters, quotes, look-alike
  and invisible Unicode, and `NUL`. The parser must accept exactly the names the rules allow, and everything it accepts
  quotes to one harmless token. A second fuzz inserts a single hostile character at every position of valid names.
* **Every name slot of every route** (38 slots: table, column, key, index, reference, operator, sort direction,
  join part, `PATCH` fields and the `DELETE /v1/index?name=` parameter) is sent 45 hand-picked hostile names (about
  1,700 requests, each of which must be refused with `400`), plus about 120 random ones per slot (each must be a
  4xx, never a 5xx). Afterwards the schema and every row must be exactly what they were before.
* **Non-string names** (numbers, `null`, arrays, objects) and **hostile `limit` / `offset`** are refused.
* **Every value slot** receives 22 hostile values: classic `OR 1=1` and `DROP TABLE` strings, quote and comment
  tricks, subselects, every placeholder style, `NULL`, look-alikes. A filter with such a value must match nothing (and
  `ne`, `not_in`, `not_like` must match everything), a delete must remove nothing, and a stored value must come back
  verbatim and be deletable as exactly one row. The same holds for joins, multi-table batches and `PATCH` defaults.
* **The keyword allowlists** and **the quoting of catalog names** (including a fuzz of the quoting function).
* **Authentication** really does run before the body is looked at.

The tests are also worth having as a safety net: when they were run against a deliberately broken copy of the code
(values pasted into the filter SQL, or the name rules loosened to allow `-` and `;`), they failed as they should.

## Limitations and roadmap

**Limitations**

- **MVCC mode is young.** Bonny relies on Turso's MVCC and concurrent transactions. It has been tested with parallel
  and overlapping writers, schema changes under load and conversion of an existing database, but no stability
  statement was found for the engine feature, so keep backups. Conflict detection relies on the engine's error
  _text_ ("write-write conflict", "schema conflict"); if a future engine version rewords those messages, retries
  would turn into `500`s (the automated tests would catch it).
- **Replica mode is unverified** against a real remote database (see [Replica mode and sync](#replica-mode-and-sync)).
- **Authentication** is one shared key, with no per-client rate limiting or failed-attempt throttling.
- **Foreign keys** have no `ON DELETE` / `ON UPDATE` actions and no composite keys, and in MVCC mode a concurrent
  parent delete and child insert can leave an orphan (see [Foreign keys](#post-v1tables)).
- **Deletes** are a separate request: a delete cannot be a step of a multi-table `batches` transaction, so "delete a
  ticker's rows, then insert the new ones" is two requests and is not atomic.
- **No UPDATE endpoint** (use an upsert batch to change rows), **no aggregates**, and **joins** are limited to
  5 tables joined directly to the base table, without table aliases.
- **Schema changes:** column types can be converted among `INTEGER`, `REAL` and `TEXT` only; dropping a column,
  changing nullability and adding a foreign key to an existing column are not supported; there is no way to drop
  or rename a table.
- **Result size:** a query returns at most 500 rows; `GET /v1/schema` always lists every table and can get large.

**Roadmap.** Ideas from the original design, and where they stand:

| Idea                                                     | Status                                              |
| -------------------------------------------------------- | --------------------------------------------------- |
| `IN`, range and `LIKE` filters                           | done (see [query](#post-v1query))                   |
| Pagination                                               | done (`limit` / `offset`)                           |
| Schema inspection                                        | done (`GET /v1/schema`)                             |
| `DELETE`                                                 | done (`POST /v1/delete`); not yet inside `batches`  |
| Joins                                                    | done, with the limits above                         |
| Background sync loop and sync observability              | done (`/v1/sync/status`)                            |
| Schema changes after creation                            | partly done (`PATCH /v1/table`, `DELETE /v1/index`) |
| `UPDATE` and aggregates                                  | not done                                            |
| A single atomic "replace all rows of a ticker" operation | not done (needs deletes inside `batches`)           |
| Versioned schema migrations                              | not done                                            |


The automated tests (the security ones are described in [SQL injection and input safety](#sql-injection-and-input-safety)) drive the real HTTP routes against temporary on-disk databases (rollback, upserts, concurrency,

## Curl walkthrough

A guided tour of the API with copy-paste `curl` commands, based on the financial-metrics data model. It works in bash
and zsh. The parts build on one another, so run them **in order** against a fresh database (the last part shows how to
start over).

### 0. Start the server

Start Bonny as described in [Getting started](#getting-started) (`cargo run` with no configuration gives
`http://127.0.0.1:3000`, no credentials, and `./bonny.db`). The commands below assume exactly that; if you
set `API_KEY`, add `-H 'x-api-key: <key>'` to every `/v1` request.

Run the commands from a second terminal, **in order**: later parts use the tables created in earlier ones.
Responses are single-line JSON; add `| jq` to pretty-print if you have [jq](https://jqlang.github.io/jq/).
(`-s` hides curl's progress meter, which only shows up when you pipe the output. Where `-w` appears it prints
the HTTP status after the body: errors have a JSON body, while creating a table or index answers
`204 No Content` with no body at all.)

### 1. Health and readiness

```bash
# Liveness: the process is up (never touches the database).
curl -s http://127.0.0.1:3000/health

# Readiness: opens a database connection, runs SELECT 1 and reports the journal mode (mvcc).
curl -s http://127.0.0.1:3000/ready
```

### 2. Create a table

```bash
curl -X POST http://127.0.0.1:3000/v1/tables -H 'content-type: application/json' -d '{"name": "financial_metrics", "columns": [{"name": "ticker", "type": "TEXT"}, {"name": "metric", "type": "TEXT"}, {"name": "period", "type": "TEXT"}, {"name": "value", "type": "REAL", "nullable": true}], "primary_key": ["ticker", "metric", "period"]}'
```

Expected: `  [HTTP 204]`. Success has no response body, so the `-w` flag is only there to show the status.
Run it again and you get `204` again: an identical table is accepted. A table with the same name
but a _different_ definition is rejected with `409` and a JSON error.

This table chose its key explicitly with `"primary_key": ["ticker", "metric", "period"]`. There are
three ways to define the primary key:

| `primary_key`         | Result                                                                 |
| --------------------- | ---------------------------------------------------------------------- |
| omitted (the default) | an `id INTEGER PRIMARY KEY` column is added and numbered automatically |
| `false`               | no primary key at all                                                  |
| `["a", "b"]`          | an explicit (possibly composite) key over your own columns             |

#### Default: an automatic integer id

Leave `primary_key` out and the table gets an `id` column that the database numbers for you
(1, 2, 3, ...). Do not declare your own `id` column in this mode.

```bash
curl -X POST http://127.0.0.1:3000/v1/tables -H 'content-type: application/json' -d '{"name": "notes", "columns": [{"name": "text", "type": "TEXT"}, {"name": "done", "type": "INTEGER", "nullable": true}]}'

# Insert without an id: the columns list simply leaves "id" out.
curl -s -X POST http://127.0.0.1:3000/v1/batch -H 'content-type: application/json' -d '{"table": "notes", "columns": ["text", "done"], "rows": [["buy milk", 0], ["call mom", null], ["write docs", 1]]}'

# The ids were assigned 1, 2, 3 and "id" comes first when you select every column.
curl -s -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "notes"}'

# You may also choose an id yourself; the next automatic one continues after the highest (here 101).
curl -s -X POST http://127.0.0.1:3000/v1/batch -H 'content-type: application/json' -d '{"table": "notes", "columns": ["id", "text"], "rows": [[100, "explicit id"]]}'
curl -s -X POST http://127.0.0.1:3000/v1/batch -H 'content-type: application/json' -d '{"table": "notes", "columns": ["text"], "rows": [["after the explicit one"]]}'

# Read the generated ids back: the newest note first.
curl -s -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "notes", "columns": ["id", "text"], "sort": [{"id": "desc"}], "limit": 2}'

# Update a row by its id: with the id in the batch, upsert (the primary key is the default conflict target).
curl -s -X POST http://127.0.0.1:3000/v1/batch -H 'content-type: application/json' -d '{"table": "notes", "columns": ["id", "text", "done"], "rows": [[1, "buy oat milk", 1]], "on_conflict": {"replace": ["text", "done"]}}'
```

The batch response does not return the generated ids, so read them back with a query as above.

#### No primary key

`"primary_key": false` creates a table without any key: no `id` column, and duplicate rows are
allowed. Useful for logs and event streams.

```bash
curl -X POST http://127.0.0.1:3000/v1/tables -H 'content-type: application/json' -d '{"name": "events", "columns": [{"name": "name", "type": "TEXT"}, {"name": "at", "type": "TEXT", "nullable": true}], "primary_key": false}'

# The same row twice: both are stored (affected: 2).
curl -s -X POST http://127.0.0.1:3000/v1/batch -H 'content-type: application/json' -d '{"table": "events", "columns": ["name", "at"], "rows": [["login", "2024-01-01"], ["login", "2024-01-01"]]}'

curl -s -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "events"}'

# Without a key there is nothing to upsert on by default: this is a 400 ("table has no primary key").
curl -X POST http://127.0.0.1:3000/v1/batch -H 'content-type: application/json' -d '{"table": "events", "columns": ["name", "at"], "rows": [["login", "2024-01-02"]], "on_conflict": "replace_all"}'
```

#### Mistakes

```bash
# 400: "id" is reserved for the automatic key. Remove the column, or choose the key yourself
# ("primary_key": ["id"] to define it, or false for none).
curl -X POST http://127.0.0.1:3000/v1/tables -H 'content-type: application/json' -d '{"name": "clash", "columns": [{"name": "id", "type": "INTEGER"}, {"name": "x", "type": "TEXT"}]}'

# 400: primary_key must be an array of column names, false, or omitted (an empty array is not "none").
curl -X POST http://127.0.0.1:3000/v1/tables -H 'content-type: application/json' -d '{"name": "bad", "columns": [{"name": "x", "type": "TEXT"}], "primary_key": []}'

# 409: the table already exists with a different kind of key (notes has the automatic id).
curl -X POST http://127.0.0.1:3000/v1/tables -H 'content-type: application/json' -d '{"name": "notes", "columns": [{"name": "text", "type": "TEXT"}, {"name": "done", "type": "INTEGER", "nullable": true}], "primary_key": false}'
```

#### Foreign keys

A column can point at a column of another table with `references`. The parent table must exist
first, so create it, give it some rows, and then create the child:

```bash
# The parent: a stocks table with an automatic id and a unique code.
curl -X POST http://127.0.0.1:3000/v1/tables -H 'content-type: application/json' -d '{"name": "stocks", "columns": [{"name": "code", "type": "TEXT"}, {"name": "name", "type": "TEXT", "nullable": true}]}'
curl -X POST http://127.0.0.1:3000/v1/indexes -H 'content-type: application/json' -d '{"name": "u_stocks_code", "table": "stocks", "columns": ["code"], "unique": true}'
curl -s -X POST http://127.0.0.1:3000/v1/batch -H 'content-type: application/json' -d '{"table": "stocks", "columns": ["code", "name"], "rows": [["AAPL", "Apple"], ["MSFT", "Microsoft"], ["GOOG", "Alphabet"]]}'

# The child: symbol_id references stocks, column id (the default), and the table has no primary key.
curl -X POST http://127.0.0.1:3000/v1/tables -H 'content-type: application/json' -d '{"name": "fact_values", "primary_key": false, "columns": [{"name": "symbol_id", "type": "integer", "references": "stocks"}, {"name": "value", "type": "REAL", "nullable": true}]}'
```

Rows that point at an existing stock are accepted; a row pointing at a stock that does not exist
is refused, and the whole batch is rolled back:

```bash
curl -s -X POST http://127.0.0.1:3000/v1/batch -H 'content-type: application/json' -d '{"table": "fact_values", "columns": ["symbol_id", "value"], "rows": [[1, 10.5], [2, 20.5], [1, 11.5]]}'

# 409: stock 99 does not exist, so even the valid first row is not written.
curl -X POST http://127.0.0.1:3000/v1/batch -H 'content-type: application/json' -d '{"table": "fact_values", "columns": ["symbol_id", "value"], "rows": [[3, 1.0], [99, 2.0]]}'
curl -s -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "fact_values", "sort": [{"value": "asc"}]}'
```

The other direction is protected too: a parent that still has children cannot be deleted
(there is no cascading), while one nobody refers to can:

```bash
# 409: stock 1 is referenced by two facts. Nothing is deleted.
curl -X POST http://127.0.0.1:3000/v1/delete -H 'content-type: application/json' -d '{"table": "stocks", "filters": {"id": 1}}'

# Stock 3 (GOOG) has no facts: deleted.
curl -X POST http://127.0.0.1:3000/v1/delete -H 'content-type: application/json' -d '{"table": "stocks", "filters": {"id": 3}}'

# Delete the children first and the parent can go.
curl -X POST http://127.0.0.1:3000/v1/delete -H 'content-type: application/json' -d '{"table": "fact_values", "filters": {"symbol_id": 2}}'
curl -X POST http://127.0.0.1:3000/v1/delete -H 'content-type: application/json' -d '{"table": "stocks", "filters": {"id": 2}}'
```

To reference a different column than `id`, use the object form. The referenced column must be unique
(a primary key or a column with a unique index, like `code` above) and have the same type:

```bash
curl -X POST http://127.0.0.1:3000/v1/tables -H 'content-type: application/json' -d '{"name": "watchlist", "primary_key": false, "columns": [{"name": "code", "type": "TEXT", "references": {"table": "stocks", "column": "code"}}]}'
curl -s -X POST http://127.0.0.1:3000/v1/batch -H 'content-type: application/json' -d '{"table": "watchlist", "columns": ["code"], "rows": [["AAPL"]]}'

# 409: there is no stock with this code.
curl -X POST http://127.0.0.1:3000/v1/batch -H 'content-type: application/json' -d '{"table": "watchlist", "columns": ["code"], "rows": [["NOPE"]]}'
```

A foreign key is checked when the table is created. These are `400`s, and nothing is created:

```bash
# The referenced table does not exist (create parents first).
curl -X POST http://127.0.0.1:3000/v1/tables -H 'content-type: application/json' -d '{"name": "bad1", "primary_key": false, "columns": [{"name": "x", "type": "INTEGER", "references": "no_such_table"}]}'

# The referenced column is not unique (stocks.name has no unique index).
curl -X POST http://127.0.0.1:3000/v1/tables -H 'content-type: application/json' -d '{"name": "bad2", "primary_key": false, "columns": [{"name": "x", "type": "TEXT", "nullable": true, "references": {"table": "stocks", "column": "name"}}]}'

# The types differ: a TEXT column cannot reference the INTEGER id.
curl -X POST http://127.0.0.1:3000/v1/tables -H 'content-type: application/json' -d '{"name": "bad3", "primary_key": false, "columns": [{"name": "x", "type": "TEXT", "references": "stocks"}]}'

# references is a table name or {"table": ..., "column": ...}; actions like cascade are not supported.
curl -X POST http://127.0.0.1:3000/v1/tables -H 'content-type: application/json' -d '{"name": "bad4", "primary_key": false, "columns": [{"name": "x", "type": "INTEGER", "references": {"table": "stocks", "on_delete": "cascade"}}]}'
```

Creating the same child table again is a `204`; the same name with different foreign keys is a
`409`. If the child table gets big, index its foreign key column (`POST /v1/indexes`): the
database has to look through the child table whenever a parent row is deleted.

#### Several tables in one request

To create a whole group of tables at once, send a `tables` list. The tables are created **together**:
if any of them fails, none is created. This one has two parent tables and a child that references both:

```bash
curl -X POST http://127.0.0.1:3000/v1/tables -H 'content-type: application/json' -d '{"tables": [{"name": "sectors", "columns": [{"name": "label", "type": "text"}]}, {"name": "analysts", "columns": [{"name": "name", "type": "text"}]}, {"name": "coverage", "primary_key": false, "columns": [{"name": "sector_id", "type": "integer", "references": "sectors"}, {"name": "analyst_id", "type": "integer", "references": "analysts"}, {"name": "since", "type": "integer"}, {"name": "rating", "type": "real"}]}]}'
```

Expected: `[HTTP 204]`. Things to know:

- **The order does not matter.** `coverage` could come first even though it points at the other two.
- **Sending it again** is a `204` too: tables that already exist with the same definition are left alone,
  and any that are missing are created.
- **All or nothing.** Here the second table (`sectors`) already exists with a different definition, so the
  request is refused with a `409` that names the table, and the new table `desks` is **not** created:

```bash
curl -X POST http://127.0.0.1:3000/v1/tables -H 'content-type: application/json' -d '{"tables": [{"name": "desks", "columns": [{"name": "id_code", "type": "text"}]}, {"name": "sectors", "columns": [{"name": "something_else", "type": "integer"}]}]}'
curl -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "desks"}'
```

The first answers `409` with `tables[1] (table "sectors"): ... already exists with a different definition`, and
the second `404`: `desks` does not exist. A bad reference is refused the same way, for example a table
that is neither in the request nor in the database (`400`, nothing created):

```bash
curl -X POST http://127.0.0.1:3000/v1/tables -H 'content-type: application/json' -d '{"tables": [{"name": "fine", "columns": [{"name": "a", "type": "text"}]}, {"name": "broken", "columns": [{"name": "x", "type": "integer", "references": "no_such_table"}]}]}'
```

### 3. Create an index

```bash
# Useful: lets you look up one metric across all tickers, ordered by period.
curl -X POST http://127.0.0.1:3000/v1/indexes -H 'content-type: application/json' -d '{"name": "idx_metrics_metric_period", "table": "financial_metrics", "columns": ["metric", "period"], "unique": false}'
```

The primary key already indexes `(ticker, metric, period)`. If you create an index that merely
repeats it, the index is still created (`204`), but the server logs a warning:

```bash
curl -X POST http://127.0.0.1:3000/v1/indexes -H 'content-type: application/json' -d '{"name": "idx_metrics_ticker_metric_period", "table": "financial_metrics", "columns": ["ticker", "metric", "period"], "unique": false}'
```

### 4. Insert a batch

```bash
curl -s -X POST http://127.0.0.1:3000/v1/batch -H 'content-type: application/json' -d '{"table": "financial_metrics", "columns": ["ticker", "metric", "period", "value"], "rows": [["AAPL", "revenue", "2024-Q1", 90753.0], ["AAPL", "revenue", "2024-Q2", 85777.0], ["AAPL", "revenue", "2024-Q3", 94930.0]], "on_conflict": "abort"}'
```

Expected: `{"rows":{"submitted":3,"affected":3},"batches":{"financial_metrics":{"submitted":3,"affected":3}}}`.
`submitted` is the rows you sent, `affected` the rows the database actually inserted or updated.
`"abort"` is the default: if any row violates a constraint (for example, the same
ticker/metric/period already exists) the **whole batch** is rolled back. Run the command a second
time to see a `409`.

### 5. Update existing rows (upsert)

Replace only the `value` column for rows that already exist, and insert the rest. This is the
"replace all metrics for a ticker" pattern.

```bash
curl -s -X POST http://127.0.0.1:3000/v1/batch -H 'content-type: application/json' -d '{"table": "financial_metrics", "columns": ["ticker", "metric", "period", "value"], "rows": [["AAPL", "revenue", "2024-Q1", 91000.0], ["AAPL", "revenue", "2024-Q4", 119575.0]], "on_conflict": {"replace": ["value"]}, "conflict_target": ["ticker", "metric", "period"]}'
```

`conflict_target` defaults to the primary key, so it can be left out here. Two other modes:

```bash
# replace_all: overwrite every non-key column that is in the batch.
curl -s -X POST http://127.0.0.1:3000/v1/batch -H 'content-type: application/json' -d '{"table": "financial_metrics", "columns": ["ticker", "metric", "period", "value"], "rows": [["AAPL", "revenue", "2024-Q2", 86000.0]], "on_conflict": "replace_all"}'

# nothing: skip rows that already exist (INSERT OR IGNORE). Only new rows are counted.
curl -s -X POST http://127.0.0.1:3000/v1/batch -H 'content-type: application/json' -d '{"table": "financial_metrics", "columns": ["ticker", "metric", "period", "value"], "rows": [["AAPL", "revenue", "2024-Q1", 0.0], ["MSFT", "revenue", "2024-Q1", 61858.0]], "on_conflict": "nothing"}'
```

### 6. Query data

Revenue history for one ticker and metric, oldest first:

```bash
curl -s -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "financial_metrics", "columns": ["period", "value"], "filters": {"ticker": "AAPL", "metric": "revenue"}, "sort": [{"period": "asc"}], "limit": 100}'
```

Expected: `{"rows":[{"period":"2024-Q1","value":91000.0}, ...],"row_count":4}`.

More variations:

```bash
# Latest period only: sort descending, take one.
curl -s -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "financial_metrics", "columns": ["period", "value"], "filters": {"ticker": "AAPL", "metric": "revenue"}, "sort": [{"period": "desc"}], "limit": 1}'

# All columns, no filter (limit defaults to 100; the maximum is 500).
curl -s -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "financial_metrics"}'

# Pagination: two rows per page. offset needs a sort so pages are stable.
curl -s -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "financial_metrics", "columns": ["ticker", "period"], "sort": [{"period": "asc"}], "limit": 2, "offset": 2}'

# First add a row whose value is missing (NULL) so the NULL examples below have something to find.
curl -s -X POST http://127.0.0.1:3000/v1/batch -H 'content-type: application/json' -d '{"table": "financial_metrics", "columns": ["ticker", "metric", "period", "value"], "rows": [["AAPL", "eps", "2024-Q1", null]]}'

# A null filter means IS NULL: rows whose value is missing.
curl -s -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "financial_metrics", "filters": {"value": null}}'
```

#### Filter operators

A plain value means "equals", and `null` means `IS NULL`. To compare in other ways, give an object of
operators instead. If an object has several operators they are combined with AND, and so are
different columns.

| Operator            | Meaning                                        | Operand                          |
| ------------------- | ---------------------------------------------- | -------------------------------- |
| `eq` / `ne`         | equal / not equal                              | a value                          |
| `gt` / `gte`        | greater than / greater than or equal           | a value                          |
| `lt` / `lte`        | less than / less than or equal                 | a value                          |
| `in` / `not_in`     | in / not in a list                             | an array of values               |
| `like` / `not_like` | pattern match (`%` any run, `_` one character) | a string, or an array of strings |
| `is_null`           | `true`: is NULL; `false`: is not NULL          | `true` or `false`                |

```bash
# IN: several tickers for one period.
curl -s -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "financial_metrics", "columns": ["ticker", "metric", "value"], "filters": {"ticker": {"in": ["AAPL", "MSFT"]}, "period": "2024-Q1"}}'

# NOT IN: everything except these metrics.
curl -s -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "financial_metrics", "columns": ["ticker", "metric", "period"], "filters": {"metric": {"not_in": ["revenue"]}}}'

# eq and ne are the explicit forms of "equals" and "not equals".
curl -s -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "financial_metrics", "columns": ["ticker", "period", "value"], "filters": {"metric": {"eq": "revenue"}, "ticker": {"ne": "MSFT"}, "period": {"ne": "2024-Q4"}}, "sort": [{"period": "asc"}]}'

# LIKE: % matches any run of characters, _ matches one. Case-insensitive for plain ASCII letters.
curl -s -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "financial_metrics", "columns": ["ticker", "period"], "filters": {"ticker": {"like": "aa%"}, "period": {"like": "%-Q4"}}}'

# LIKE with several patterns matches ANY of them (OR); NOT LIKE with several matches NONE of them (AND).
curl -s -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "financial_metrics", "columns": ["ticker", "period"], "filters": {"ticker": {"like": ["AA%", "MS%"]}, "period": {"not_like": ["%-Q1", "%-Q4"]}}, "sort": [{"ticker": "asc"}, {"period": "asc"}]}'

# Greater / less than: two operators on one column make a range (90000 < value < 100000).
curl -s -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "financial_metrics", "columns": ["period", "value"], "filters": {"ticker": "AAPL", "value": {"gt": 90000, "lt": 100000}}, "sort": [{"period": "asc"}]}'

# gte / lte include the boundary: 86000 <= value <= 94930.
curl -s -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "financial_metrics", "columns": ["period", "value"], "filters": {"ticker": "AAPL", "metric": "revenue", "value": {"gte": 86000, "lte": 94930}}, "sort": [{"period": "asc"}]}'

# Text compares too: periods after 2024-Q2.
curl -s -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "financial_metrics", "columns": ["ticker", "period"], "filters": {"period": {"gt": "2024-Q2"}}}'

# IS NULL / IS NOT NULL (the eps row added above has no value).
curl -s -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "financial_metrics", "columns": ["ticker", "metric", "period"], "filters": {"value": {"is_null": true}}}'
curl -s -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "financial_metrics", "columns": ["ticker", "period"], "filters": {"value": {"is_null": false}}, "limit": 2, "sort": [{"ticker": "asc"}, {"period": "asc"}]}'
```

**NULL rows and comparisons.** As in SQL, a comparison is never true for a missing value, so `ne`,
`gt`, `not_in`, `not_like` and friends leave NULL rows out. Compare these two (the second finds the
eps row, the first does not):

```bash
curl -s -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "financial_metrics", "columns": ["ticker", "metric"], "filters": {"ticker": "AAPL", "value": {"ne": 91000}}, "sort": [{"metric": "asc"}, {"period": "asc"}]}'
curl -s -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "financial_metrics", "columns": ["ticker", "metric"], "filters": {"ticker": "AAPL", "value": {"is_null": true}}}'
```

An empty list is allowed: `{"in": []}` matches nothing and `{"not_in": []}` matches everything.

#### Sorting

`sort` is an array with one single-column object per sort key, each `"asc"` or `"desc"`. The array
order is the priority: the first entry is the main sort, later ones break ties.

```bash
# One key, descending.
curl -s -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "financial_metrics", "columns": ["ticker", "period", "value"], "filters": {"metric": "revenue"}, "sort": [{"value": "desc"}], "limit": 3}'

# Several keys: oldest period first, and within a period ordered by ticker (A to Z).
# The 2024-Q1 rows of AAPL and MSFT come first, then 2024-Q2, and so on.
curl -s -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "financial_metrics", "columns": ["period", "ticker", "value"], "filters": {"metric": "revenue"}, "sort": [{"period": "asc"}, {"ticker": "asc"}], "limit": 4}'

# Swap the two entries and the result changes: now all of AAPL's periods come before any MSFT row.
curl -s -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "financial_metrics", "columns": ["ticker", "period", "value"], "filters": {"metric": "revenue"}, "sort": [{"ticker": "asc"}, {"period": "asc"}], "limit": 4}'

# Filters, sort and paging together: rows 3 and 4 of "ticker A-Z, newest period first".
# The direction is case-insensitive ("ASC" and "DESC" work).
curl -s -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "financial_metrics", "columns": ["ticker", "period", "value"], "filters": {"metric": "revenue"}, "sort": [{"ticker": "ASC"}, {"period": "DESC"}], "limit": 2, "offset": 2}'
```

### 7. See the atomic rollback

The second row below collides with an existing primary key, so the first row must not be kept:

```bash
curl -X POST http://127.0.0.1:3000/v1/batch -H 'content-type: application/json' -d '{"table": "financial_metrics", "columns": ["ticker", "metric", "period", "value"], "rows": [["ZZZZ", "revenue", "2024-Q1", 1.0], ["AAPL", "revenue", "2024-Q1", 2.0]]}'

# Expect row_count 0: ZZZZ was rolled back together with the failing row.
curl -s -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "financial_metrics", "filters": {"ticker": "ZZZZ"}}'
```

The first call answers `409` with `constraint violation at row 1; the whole batch was rolled back`.

### 8. Several tables in one transaction

To write more than one table atomically, send a `batches` array. The steps run in order inside one
transaction. First a second table:

```bash
curl -X POST http://127.0.0.1:3000/v1/tables -H 'content-type: application/json' -d '{"name": "companies", "columns": [{"name": "ticker", "type": "TEXT"}, {"name": "name", "type": "TEXT", "nullable": true}], "primary_key": ["ticker"]}'
```

Then insert into both tables at once:

```bash
curl -s -X POST http://127.0.0.1:3000/v1/batch -H 'content-type: application/json' -d '{"batches": [{"table": "companies", "columns": ["ticker", "name"], "rows": [["AAPL", "Apple"], ["MSFT", "Microsoft"], ["GOOG", "Alphabet"]]}, {"table": "financial_metrics", "columns": ["ticker", "metric", "period", "value"], "rows": [["GOOG", "revenue", "2024-Q1", 86300.0]]}]}'
```

Expected: `{"rows":{"submitted":4,"affected":4},"batches":{"companies":{"submitted":3,"affected":3},"financial_metrics":{"submitted":1,"affected":1}}}`.
`rows` is the total, `batches` the per-table breakdown. Each step has its own `on_conflict`, and the
same table may appear in several steps (their counts are added up).

If any step fails, **all** steps are rolled back. Here step 0 is fine, but step 1 repeats an
existing primary key:

```bash
curl -X POST http://127.0.0.1:3000/v1/batch -H 'content-type: application/json' -d '{"batches": [{"table": "companies", "columns": ["ticker", "name"], "rows": [["ZZZZ", "Rolled back"]]}, {"table": "financial_metrics", "columns": ["ticker", "metric", "period", "value"], "rows": [["AAPL", "revenue", "2024-Q1", 2.0]]}]}'

# Expect row_count 0: the company from step 0 was rolled back together with the failing step.
curl -s -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "companies", "filters": {"ticker": "ZZZZ"}}'
```

The first call answers `409` with `batches[1] (table "financial_metrics"): constraint violation at row 0; the whole request was rolled back`.
Everything is validated before the transaction starts, so a typo in a later step (unknown column,
bad value, missing table) is a `400`/`404` that also names the step and writes nothing.

#### Batch request format

A body is either **one batch object** (part 4) or an **envelope** with a `batches` array of them:

```json
{"batches": [ {"table": "...", "columns": [...], "rows": [...]}, {"table": "...", ...} ]}
```

Each step may set its own `on_conflict` and `conflict_target`. The response always has the same
shape: `rows` (totals) and `batches` (per table). Some more examples:

```bash
# Per-step conflict handling: upsert one table, skip existing rows in the other.
curl -X POST http://127.0.0.1:3000/v1/batch -H 'content-type: application/json' -d '{"batches": [{"table": "companies", "columns": ["ticker", "name"], "rows": [["AAPL", "Apple Inc."]], "on_conflict": {"replace": ["name"]}}, {"table": "financial_metrics", "columns": ["ticker", "metric", "period", "value"], "rows": [["MSFT", "revenue", "2024-Q1", 1.0], ["MSFT", "revenue", "2024-Q2", 64727.0]], "on_conflict": "nothing"}]}'

# The same table in several steps: its counts are added up under one key in "batches".
curl -s -X POST http://127.0.0.1:3000/v1/batch -H 'content-type: application/json' -d '{"batches": [{"table": "financial_metrics", "columns": ["ticker", "metric", "period", "value"], "rows": [["GOOG", "revenue", "2024-Q2", 90000.0], ["GOOG", "revenue", "2024-Q3", 91000.0]]}, {"table": "companies", "columns": ["ticker", "name"], "rows": [["AMZN", "Amazon"]]}, {"table": "financial_metrics", "columns": ["ticker", "metric", "period", "value"], "rows": [["AMZN", "revenue", "2024-Q1", 143300.0]]}]}'

# An empty list is a valid no-op.
curl -s -X POST http://127.0.0.1:3000/v1/batch -H 'content-type: application/json' -d '{"batches": []}'
```

Expected, in order:

- `{"rows":{"submitted":3,"affected":2},"batches":{"companies":{"submitted":1,"affected":1},"financial_metrics":{"submitted":2,"affected":1}}}`
  (one MSFT row already existed and was skipped, so `submitted` is larger than `affected`)
- `{"rows":{"submitted":4,"affected":4},"batches":{"financial_metrics":{"submitted":3,"affected":3},"companies":{"submitted":1,"affected":1}}}`
- `{"rows":{"submitted":0,"affected":0},"batches":{}}`

Everything is validated **before** the transaction starts, so a mistake in a later step writes nothing
from the earlier ones. Step 0 below is fine, but step 1 has a misspelled column; the error names the
step, and the check afterwards shows the company from step 0 was not written:

```bash
curl -X POST http://127.0.0.1:3000/v1/batch -H 'content-type: application/json' -d '{"batches": [{"table": "companies", "columns": ["ticker", "name"], "rows": [["NEWCO", "New Co"]]}, {"table": "financial_metrics", "columns": ["ticker", "metric", "period", "valeu"], "rows": [["NEWCO", "revenue", "2024-Q1", 1.0]]}]}'
curl -s -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "companies", "filters": {"ticker": "NEWCO"}}'

# A table that does not exist in a later step is a 404 that names the step.
curl -X POST http://127.0.0.1:3000/v1/batch -H 'content-type: application/json' -d '{"batches": [{"table": "companies", "columns": ["ticker", "name"], "rows": [["NEWCO", "New Co"]]}, {"table": "no_such_table", "columns": ["a"], "rows": [[1]]}]}'

# So is a bad value (here an array) in a later step: a 400 naming the step and the row.
curl -X POST http://127.0.0.1:3000/v1/batch -H 'content-type: application/json' -d '{"batches": [{"table": "companies", "columns": ["ticker", "name"], "rows": [["NEWCO", "New Co"]]}, {"table": "financial_metrics", "columns": ["ticker", "metric", "period", "value"], "rows": [["NEWCO", "revenue", "2024-Q1", 1.0], ["NEWCO", "revenue", "2024-Q2", [1, 2]]]}]}'
```

The request limits apply to the whole `batches` array (20 steps, 5,000 rows, 100,000 values by
default; see the reference above to change them).

### 9. Delete rows

`POST /v1/delete` removes the rows that match `filters`, which work exactly like the filters of
`/v1/query` (plain values, `null`, `in`, `like`, `gt`, ... combined with AND). The answer is the
number of rows removed.

```bash
# Delete by equality: the AMZN rows of the financial_metrics table.
curl -s -X POST http://127.0.0.1:3000/v1/delete -H 'content-type: application/json' -d '{"table": "financial_metrics", "filters": {"ticker": "AMZN"}}'

# Operators and several columns together: eps rows whose value is missing.
curl -s -X POST http://127.0.0.1:3000/v1/delete -H 'content-type: application/json' -d '{"table": "financial_metrics", "filters": {"metric": {"in": ["eps"]}, "value": {"is_null": true}}}'

# By id on a table with the automatic id (the notes of part 2): ids 100 and above.
curl -s -X POST http://127.0.0.1:3000/v1/delete -H 'content-type: application/json' -d '{"table": "notes", "filters": {"id": {"gte": 100}}}'

# See what is left.
curl -s -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "notes", "sort": [{"id": "asc"}]}'

# Deleting nothing is a success, not an error: "deleted" is 0, so repeating a delete is safe.
curl -s -X POST http://127.0.0.1:3000/v1/delete -H 'content-type: application/json' -d '{"table": "financial_metrics", "filters": {"ticker": "AMZN"}}'
```

Expected, in order: `{"rows":{"deleted":1}}`, `{"rows":{"deleted":1}}`, `{"rows":{"deleted":2}}`, the three
remaining notes (ids 1, 2 and 3), and `{"rows":{"deleted":0}}`.

#### Safety rules

A forgotten filter must not wipe a table, so `filters` is required. To delete **every** row you have
to ask for it explicitly with `"all": true`. The optional `max_rows` is a guard: if more rows than
that would be deleted, nothing is deleted at all.

```bash
# 400: no filters. Missing, empty and "all": false are all refused.
curl -X POST http://127.0.0.1:3000/v1/delete -H 'content-type: application/json' -d '{"table": "notes"}'
curl -X POST http://127.0.0.1:3000/v1/delete -H 'content-type: application/json' -d '{"table": "notes", "filters": {}}'

# 400: "all" and filters cannot be combined.
curl -X POST http://127.0.0.1:3000/v1/delete -H 'content-type: application/json' -d '{"table": "notes", "all": true, "filters": {"id": 1}}'

# 409 too_many_rows: two "login" events match but only one is allowed. Nothing was deleted...
curl -X POST http://127.0.0.1:3000/v1/delete -H 'content-type: application/json' -d '{"table": "events", "filters": {"name": "login"}, "max_rows": 1}'
# ...as this shows (still 2 rows).
curl -s -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "events"}'

# With a large enough guard it goes through.
curl -s -X POST http://127.0.0.1:3000/v1/delete -H 'content-type: application/json' -d '{"table": "events", "filters": {"name": "login"}, "max_rows": 2}'

# Delete every row, explicitly (the table itself stays): the three notes that were left.
curl -s -X POST http://127.0.0.1:3000/v1/delete -H 'content-type: application/json' -d '{"table": "notes", "all": true}'
```

The server can also set a ceiling for every delete with the `MAX_DELETE_ROWS` environment variable
(no limit by default); a request's `max_rows` can only lower it.

#### Mistakes

```bash
# 404: unknown table.
curl -X POST http://127.0.0.1:3000/v1/delete -H 'content-type: application/json' -d '{"table": "no_such_table", "filters": {"a": 1}}'

# 400: unknown column (checked, so a typo can never match every row).
curl -X POST http://127.0.0.1:3000/v1/delete -H 'content-type: application/json' -d '{"table": "financial_metrics", "filters": {"tickr": "AAPL"}}'

# 400: only table, filters, all and max_rows exist: there is no sort or limit.
curl -X POST http://127.0.0.1:3000/v1/delete -H 'content-type: application/json' -d '{"table": "financial_metrics", "filters": {"ticker": "AAPL"}, "limit": 1}'
```

A delete is its own transaction. To replace a ticker's rows you currently send a delete and then a
batch insert as two requests; they are not atomic together.

### 10. Binary data

JSON has no binary type, so blobs are written and read as a tagged object:

```bash
curl -X POST http://127.0.0.1:3000/v1/tables -H 'content-type: application/json' -d '{"name": "files", "columns": [{"name": "id", "type": "INTEGER"}, {"name": "data", "type": "BLOB"}], "primary_key": ["id"]}'

curl -s -X POST http://127.0.0.1:3000/v1/batch -H 'content-type: application/json' -d '{"table": "files", "columns": ["id", "data"], "rows": [[1, {"$type": "blob", "base64": "AAECAw=="}]]}'

curl -s -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "files"}'
```

### 11. Errors you can expect

Every error is JSON: `{"error": "...", "code": "..."}`.

```bash
# 400: identifiers are restricted to letters, digits and underscores (no SQL can sneak in).
curl -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "financial_metrics; DROP TABLE financial_metrics"}'

# 404: unknown table.
curl -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "no_such_table"}'

# 400: unknown column.
curl -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "financial_metrics", "columns": ["nope"]}'

# 400: misspelled field names are rejected instead of silently ignored ("filter" vs "filters").
curl -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "financial_metrics", "filter": {"ticker": "AAPL"}}'
```

#### Filter, sort and batch mistakes

Mistakes in the newer request shapes are `400`s that say what is wrong:

```bash
# Unknown operator: the message lists the supported ones.
curl -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "financial_metrics", "filters": {"value": {"between": [1, 2]}}}'

# null is not allowed inside a comparison; use is_null instead.
curl -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "financial_metrics", "filters": {"value": {"gt": null}}}'

# "in" needs an array.
curl -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "financial_metrics", "filters": {"ticker": {"in": "AAPL"}}}'

# sort is an array of one-column objects; the older object form and "order_by" are rejected.
curl -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "financial_metrics", "sort": {"period": "asc"}}'
curl -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "financial_metrics", "order_by": {"column": "period"}}'

# Each sort entry has exactly one column, and the direction must be asc or desc.
curl -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "financial_metrics", "sort": [{"period": "asc", "ticker": "desc"}]}'
curl -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "financial_metrics", "sort": [{"period": "up"}]}'

# Batch bodies: a bare array is not accepted, and the envelope cannot be mixed with a top-level batch.
curl -X POST http://127.0.0.1:3000/v1/batch -H 'content-type: application/json' -d '[{"table": "companies", "columns": ["ticker"], "rows": [["X"]]}]'
curl -X POST http://127.0.0.1:3000/v1/batch -H 'content-type: application/json' -d '{"batches": [], "table": "companies"}'
```

### 12. Inspect the schema

`GET /v1/schema` lists every table with its columns, primary key, foreign keys and indexes:

```bash
curl -s http://127.0.0.1:3000/v1/schema
```

The answer is one long line, so it helps to pretty-print it if you have [jq](https://jqlang.github.io/jq/)
(`curl -s http://127.0.0.1:3000/v1/schema | jq`) or Python (`... | python3 -m json.tool`).
For the `stocks` and `fact_values` tables of part 2, the relevant part of the answer looks like this
(shortened to two tables, and reformatted):

```json
{
  "tables": [
    {
      "name": "fact_values",
      "primary_key": [],
      "columns": [
        {
          "name": "symbol_id",
          "type": "INTEGER",
          "nullable": false,
          "auto_id": false,
          "references": { "table": "stocks", "column": "id" }
        },
        { "name": "value", "type": "REAL", "nullable": true, "auto_id": false }
      ],
      "indexes": []
    },
    {
      "name": "stocks",
      "primary_key": ["id"],
      "columns": [
        { "name": "id", "type": "INTEGER", "nullable": false, "auto_id": true },
        { "name": "code", "type": "TEXT", "nullable": false, "auto_id": false },
        { "name": "name", "type": "TEXT", "nullable": true, "auto_id": false }
      ],
      "indexes": [{ "name": "u_stocks_code", "unique": true, "columns": ["code"] }]
    }
  ]
}
```

How to read it:

- `tables` are sorted by name, and `columns` are in the order they were declared.
- `primary_key` lists the key columns in key order; an empty list means the table has no primary key.
- `nullable` says whether the column accepts `NULL` (key columns never do).
- `auto_id: true` marks the column the database numbers for you when an insert leaves it out
  (the automatic `id`, or any single `INTEGER` primary key).
- `references` appears only on foreign key columns, in the same form you used to create them.
- `indexes` are the ones made with `POST /v1/indexes`, sorted by name, with `unique` and the
  indexed `columns` in index order. The primary key's own index is not listed.

Tables the API cannot use (the database's internal tables, views, odd names) are left out, and the
list always reflects the current state: create a table or an index and ask again.

### 13. Change a table: add, retype and rename columns

`PATCH /v1/table` looks at one column and makes it match what you ask for: it **adds** the column if it
does not exist, **changes its type** if it differs, and **renames** it if you give `rename`. Every
answer is `204 No Content`. A request describes the end result, so sending it twice does no harm.

A table to play with (`amount` is NOT NULL, `qty` and `note` accept NULL; the table also gets an `id`):

```bash
curl -X POST http://127.0.0.1:3000/v1/tables -H 'content-type: application/json' -d '{"name": "readings", "columns": [{"name": "amount", "type": "TEXT"}, {"name": "qty", "type": "TEXT", "nullable": true}, {"name": "note", "type": "TEXT", "nullable": true}]}'
curl -s -X POST http://127.0.0.1:3000/v1/batch -H 'content-type: application/json' -d '{"table": "readings", "columns": ["amount", "qty", "note"], "rows": [["10", "1", "a"], ["20", "2", "b"], ["30", null, "c"]]}'
```

#### Add a column

```bash
# A nullable column: existing rows get NULL.
curl -X PATCH http://127.0.0.1:3000/v1/table -H 'content-type: application/json' -d '{"table": "readings", "column": "unit", "type": "TEXT", "nullable": true}'

# With "default", existing rows get that value instead (once; the column has no default afterwards).
curl -X PATCH http://127.0.0.1:3000/v1/table -H 'content-type: application/json' -d '{"table": "readings", "column": "source", "type": "TEXT", "nullable": true, "default": "sensor"}'

# NOT NULL (the default for new columns) on a table that has rows needs a value for those rows: 400.
curl -X PATCH http://127.0.0.1:3000/v1/table -H 'content-type: application/json' -d '{"table": "readings", "column": "checked", "type": "INTEGER"}'

# ...so give one. The table is rebuilt behind the scenes; ids, order and indexes are kept.
curl -X PATCH http://127.0.0.1:3000/v1/table -H 'content-type: application/json' -d '{"table": "readings", "column": "checked", "type": "INTEGER", "default": 0}'

# Asking for the same column again changes nothing.
curl -X PATCH http://127.0.0.1:3000/v1/table -H 'content-type: application/json' -d '{"table": "readings", "column": "checked", "type": "INTEGER"}'
curl -s -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "readings"}'
```

A new column can also be a foreign key: add `"references": "stocks"` or
`{"table": "stocks", "column": "code"}` (the same checks as when creating a table apply).

#### Change a column's type

`qty` is text such as `"1"`. Converting it to `INTEGER` casts the values; `NULL` stays `NULL`:

```bash
curl -X PATCH http://127.0.0.1:3000/v1/table -H 'content-type: application/json' -d '{"table": "readings", "column": "qty", "type": "integer"}'
curl -s -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "readings", "columns": ["id", "qty"]}'
```

Expected: `{"id":1,"qty":1}`, `{"id":2,"qty":2}`, `{"id":3,"qty":null}`: real numbers now. A nullable column is
changed in place and **moves to the end** of the table. `amount` is NOT NULL, so changing it rebuilds the
table, which keeps the column order and the NOT NULL:

```bash
curl -X PATCH http://127.0.0.1:3000/v1/table -H 'content-type: application/json' -d '{"table": "readings", "column": "amount", "type": "INTEGER"}'
curl -s -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "readings", "filters": {"amount": {"gt": 15}}, "sort": [{"id": "asc"}]}'
```

Casting can silently damage data (`"abc"` would become `0`), so Bonny checks every value first and
refuses if any would change. Nothing is modified in that case:

```bash
curl -X POST http://127.0.0.1:3000/v1/tables -H 'content-type: application/json' -d '{"name": "messy", "columns": [{"name": "v", "type": "TEXT", "nullable": true}]}'
curl -s -X POST http://127.0.0.1:3000/v1/batch -H 'content-type: application/json' -d '{"table": "messy", "columns": ["v"], "rows": [["42"], ["007"], ["abc"], [null]]}'

# 409 lossy_conversion: "007" and "abc" would change. The message lists examples.
curl -X PATCH http://127.0.0.1:3000/v1/table -H 'content-type: application/json' -d '{"table": "messy", "column": "v", "type": "INTEGER"}'

# If that is what you want, say so with "lossy": true (007 becomes 7, abc becomes 0).
curl -X PATCH http://127.0.0.1:3000/v1/table -H 'content-type: application/json' -d '{"table": "messy", "column": "v", "type": "INTEGER", "lossy": true}'
curl -s -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "messy", "columns": ["v"], "sort": [{"id": "asc"}]}'
```

Supported conversions are between `INTEGER`, `REAL` and `TEXT`. Primary key columns, foreign key columns
and columns that other tables reference cannot be retyped:

```bash
# 409: stocks.id is the primary key.
curl -X PATCH http://127.0.0.1:3000/v1/table -H 'content-type: application/json' -d '{"table": "stocks", "column": "id", "type": "text"}'

# 409: fact_values.symbol_id is a foreign key to stocks.id.
curl -X PATCH http://127.0.0.1:3000/v1/table -H 'content-type: application/json' -d '{"table": "fact_values", "column": "symbol_id", "type": "text"}'
```

#### Rename a column

```bash
curl -X PATCH http://127.0.0.1:3000/v1/table -H 'content-type: application/json' -d '{"table": "readings", "column": "amount", "rename": "weight"}'

# The same request again: the column is already called weight, so nothing happens. In particular
# no new, empty "amount" column is added.
curl -X PATCH http://127.0.0.1:3000/v1/table -H 'content-type: application/json' -d '{"table": "readings", "column": "amount", "rename": "weight"}'

# Type and name together (and repeating that is fine too).
curl -X PATCH http://127.0.0.1:3000/v1/table -H 'content-type: application/json' -d '{"table": "readings", "column": "qty", "type": "real", "rename": "quantity"}'
curl -s -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "readings", "sort": [{"id": "asc"}]}'
```

Indexes and foreign keys that involve a renamed column follow its new name. Clients that still use the
old name will get errors, so rename with care.

#### Mistakes

```bash
# 404: no such table.
curl -X PATCH http://127.0.0.1:3000/v1/table -H 'content-type: application/json' -d '{"table": "no_such_table", "column": "a", "type": "TEXT"}'

# 400: nothing to do; give a type, a rename, or both.
curl -X PATCH http://127.0.0.1:3000/v1/table -H 'content-type: application/json' -d '{"table": "readings", "column": "note"}'

# 400: this column does not exist, so there is nothing to rename (leave "rename" out to add it).
curl -X PATCH http://127.0.0.1:3000/v1/table -H 'content-type: application/json' -d '{"table": "readings", "column": "ghost", "rename": "spirit"}'

# 409: the new name is already taken by another column.
curl -X PATCH http://127.0.0.1:3000/v1/table -H 'content-type: application/json' -d '{"table": "readings", "column": "note", "rename": "unit"}'

# 409: the nullability of an existing column cannot be changed here.
curl -X PATCH http://127.0.0.1:3000/v1/table -H 'content-type: application/json' -d '{"table": "readings", "column": "note", "type": "TEXT", "nullable": false}'
```

Changing a type rewrites every row, so it takes time in proportion to the size of the table, and it
is all-or-nothing: if anything fails, the table is exactly as it was.

### 14. Drop an index

`DELETE /v1/index?name=<index>` drops an index you no longer need. First make one and look at it:

```bash
curl -X POST http://127.0.0.1:3000/v1/indexes -H 'content-type: application/json' -d '{"name": "idx_readings_weight", "table": "readings", "columns": ["weight"]}'
curl -s http://127.0.0.1:3000/v1/schema | python3 -c "import sys,json; print([i for t in json.load(sys.stdin)['tables'] if t['name']=='readings' for i in t['indexes']])"

# Drop it: 204 No Content.
curl -X DELETE "http://127.0.0.1:3000/v1/index?name=idx_readings_weight"

# 404: it is gone now.
curl -X DELETE "http://127.0.0.1:3000/v1/index?name=idx_readings_weight"

# 400: financial_metrics is a table, not an index. A missing name is a 400 as well.
curl -X DELETE "http://127.0.0.1:3000/v1/index?name=financial_metrics"
curl -X DELETE "http://127.0.0.1:3000/v1/index"
```

An index that makes a column unique for another table's foreign key cannot be dropped, because every
later insert into that table would be refused. Here `watchlist.code` references `stocks.code`, which
is unique thanks to `u_stocks_code` (part 2):

```bash
# 409: the foreign key of watchlist.code needs this index. Nothing is dropped.
curl -X DELETE "http://127.0.0.1:3000/v1/index?name=u_stocks_code"
```

### 15. Join tables

`POST /v1/query` can join other tables to the one in `table`. Three tables to try it on: a table of
`instruments`, a table of `metrics`, and `observations` that point at both through foreign keys:

```bash
curl -X POST http://127.0.0.1:3000/v1/tables -H 'content-type: application/json' -d '{"name": "instruments", "columns": [{"name": "symbol", "type": "TEXT"}, {"name": "name", "type": "TEXT", "nullable": true}]}'
curl -X POST http://127.0.0.1:3000/v1/indexes -H 'content-type: application/json' -d '{"name": "u_instruments_symbol", "table": "instruments", "columns": ["symbol"], "unique": true}'
curl -X POST http://127.0.0.1:3000/v1/tables -H 'content-type: application/json' -d '{"name": "metrics", "columns": [{"name": "name", "type": "TEXT"}]}'
curl -X POST http://127.0.0.1:3000/v1/tables -H 'content-type: application/json' -d '{"name": "observations", "columns": [{"name": "instrument_id", "type": "INTEGER", "references": "instruments"}, {"name": "metric_id", "type": "INTEGER", "references": "metrics"}, {"name": "value", "type": "REAL"}, {"name": "ordinal", "type": "INTEGER"}, {"name": "frequency", "type": "INTEGER"}]}'

# One request fills all three (parents first). Instruments get ids 1-3 and metrics ids 1-3.
curl -s -X POST http://127.0.0.1:3000/v1/batch -H 'content-type: application/json' -d '{"batches": [{"table": "instruments", "columns": ["symbol", "name"], "rows": [["AAPL", "Apple"], ["MSFT", "Microsoft"], ["GOOG", "Alphabet"]]}, {"table": "metrics", "columns": ["name"], "rows": [["eps"], ["revenue"], ["margin"]]}, {"table": "observations", "columns": ["instrument_id", "metric_id", "value", "ordinal", "frequency"], "rows": [[1, 1, 1.5, 3, 1], [1, 1, 1.2, 2, 1], [1, 1, 9.9, 1, 4], [1, 2, 100.0, 1, 1], [2, 1, 2.5, 1, 1], [2, 2, 200.0, 1, 1]]}]}'
```

#### A join

`join` maps each table to join to the **column of the base table that holds its key**. `columns` lists
the columns wanted **per table**, and `filters` and `sort` may name a column as `table.column`:

```bash
curl -s -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "observations", "join": {"instruments": "instrument_id", "metrics": "metric_id"}, "columns": {"observations": ["value", "ordinal"], "instruments": ["symbol"], "metrics": ["name"]}, "filters": {"metrics.name": "eps", "instruments.symbol": "AAPL", "frequency": 1}, "sort": [{"ordinal": "asc"}]}'
```

Expected: `{"rows":[{"value":1.2,"ordinal":2,"symbol":"AAPL","name":"eps"},{"value":1.5,"ordinal":3,"symbol":"AAPL","name":"eps"}],"row_count":2}`.

- The foreign keys tell Bonny what to compare: `observations.instrument_id` with the column of
  `instruments` it references (`id`). Without a foreign key the joined table's `id` is used.
- `frequency` and `ordinal` have no `table.` in front: that is fine when **only one** table of the query
  has a column of that name. `name` exists in both `instruments` and `metrics`, so it has to be written
  `metrics.name`.
- The joined tables are inner joined: rows without a match on the other side are left out.

`columns` can be written in a few equivalent ways: an object per table (above), a list holding that
object, or a list of names with the table in front when needed:

```bash
curl -s -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "observations", "join": {"instruments": "instrument_id", "metrics": "metric_id"}, "columns": ["observations.value", "instruments.symbol", "metrics.name"], "filters": {"observations.ordinal": 3}}'
curl -s -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "observations", "join": {"instruments": "instrument_id"}, "columns": [{"observations": ["value"], "instruments": ["symbol"]}], "filters": {"value": {"gt": 100}}, "sort": [{"value": "desc"}]}'
```

#### Same column name in two tables

Every table has an `id`, so selecting `id` from two tables would give the result two columns with the
same name. That is an error, until you name one of them with `as`:

```bash
curl -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "observations", "join": {"instruments": "instrument_id"}, "columns": {"observations": ["id"], "instruments": ["id"]}}'
curl -s -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "observations", "join": {"instruments": "instrument_id"}, "columns": {"observations": [{"column": "id", "as": "observation_id"}, "value"], "instruments": [{"column": "id", "as": "instrument_id"}, "symbol"]}, "filters": {"ordinal": 3}}'
```

#### Other joins

The join column can be spelled out, which allows joining in the other direction (a parent to its
children) or on columns that are not foreign keys. `"type": "left"` keeps rows that have no match
(their columns from the joined table are `null`):

```bash
# From a parent to its children: every observation of every instrument. GOOG has none, so it is missing...
curl -s -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "instruments", "join": {"observations": {"column": "id", "to": "instrument_id"}}, "columns": {"instruments": ["symbol"], "observations": ["value"]}, "filters": {"observations.metric_id": 2}, "sort": [{"symbol": "asc"}]}'

# ...unless it is a left join: GOOG comes back with a null value.
curl -s -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "instruments", "join": {"observations": {"column": "id", "to": "instrument_id", "type": "left"}}, "columns": {"instruments": ["symbol"], "observations": ["value"]}, "filters": {"symbol": "GOOG"}}'
```

Up to 5 tables can be joined to the base table. Each is joined directly to it (a table cannot be joined
through another joined table), and a table cannot be joined to itself.

#### Mistakes

```bash
# 400: "name" exists in instruments and metrics.
curl -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "observations", "join": {"instruments": "instrument_id", "metrics": "metric_id"}, "columns": {"observations": ["value"]}, "filters": {"name": "eps"}}'

# 400: a joined query needs its columns spelled out.
curl -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "observations", "join": {"instruments": "instrument_id"}}'

# 400: this column does not exist (never silently read as text).
curl -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "observations", "join": {"instruments": "instrument_id"}, "columns": {"instruments": ["ticker"]}}'

# 404: the joined table does not exist.
curl -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "observations", "join": {"nope": "instrument_id"}, "columns": {"nope": ["x"]}}'

# 400: the join column must be a column of the base table (observations has no column "nope").
curl -X POST http://127.0.0.1:3000/v1/query -H 'content-type: application/json' -d '{"table": "observations", "join": {"metrics": "nope"}, "columns": {"metrics": ["name"]}}'
```

Joins are fastest when the compared columns are indexed (a primary key always is); an unindexed join
column makes the database scan the table.

### 16. Sync with a remote database (replica mode only)

These routes exist only when the server was started with `TURSO_DATABASE_URL` and
`TURSO_AUTH_TOKEN`; otherwise they return `404`. Replica mode also pushes and pulls automatically
every 30 seconds, so you only need these to force a sync.

```bash
# Send local writes to the remote.
curl -s -X POST http://127.0.0.1:3000/v1/sync/push

# Fetch remote changes. Answers {"ok":true,"changed":true|false}.
curl -s -X POST http://127.0.0.1:3000/v1/sync/pull

# Last push/pull times, last error, and how many local changes are still unpushed.
curl -s http://127.0.0.1:3000/v1/sync/status
```
